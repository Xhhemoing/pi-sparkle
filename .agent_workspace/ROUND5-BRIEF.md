**Evidence (reviewer-reproduced at HEAD, unmodified `startFlowchartRun`):** a clustered child returning `outcome: SUCCESS` with `verification: { kind: "FAILED" }` produces `TRACKING_ASSESSMENT` → `GATE_TRANSITION` → `RUN_BLOCKED` (the gate's queue_analysis, whose own comment says "replay/resume treat RUN_BLOCKED as terminal BLOCKED until an explicit unblock"), and then the loop appends `RUN_FAILED` (`persistFailed` guards only on a prior `RUN_FAILED`, `flowchart-run.ts:583-589`). `replayRun` reports `anomalies: ["multiple terminal events"]` (`replay.ts:124-129` sets `sawTerminal` on `RUN_BLOCKED`) on a production-ordinary log, and the FAILED buries a state `RESUMABLE_CRASH_STATUSES` calls operator-actionable. Several suites assert `anomalies` deep-equals `[]`.
**Change:** decide, with parent sign-off, which subsystem is right: (a) the loop respects the gate — `persistFailed` (and `persistBlocked`'s interplay) refuses when the log already replays BLOCKED, so a verification-failed run ends BLOCKED with the analysis queued, resumable after an unblock; or (b) BLOCKED→FAILED escalation is legitimate — then replay's anomaly rule and wording must accept exactly that ordering (and only that ordering), and the operator meaning is documented. Either way: pin the decided log shape for the verification-failed case, keep exactly-one-terminal semantics coherent, and fix or annotate the suites that relied on the ambiguity. The reviewer's repro (child result SUCCESS + verification FAILED through `compileChildrenToFlowchart`, one node) is the test seed.
**Ownership:** `src/run/flowchart-run.ts` (sole), `src/run/replay.ts`, `test/unit/run/replay.test.ts`, a new gate-outcome test file under `test/unit/run/` or additions to `test/unit/tracking/`.

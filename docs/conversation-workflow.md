# 对话入口与长期任务衔接

这是在现有四职责架构上提出的交互接线方案。2026-10-18 的 [C1/C2-A 宿主切片](conversation-host.md)已补上结构化查询/直接任务、会话内焦点与 M4-A 本次表达偏好；当前结果见[验证记录](../archive/reports/2026-10-18-conversation-presentation.md)。P1 已补显式宿主配置的扩展工具接线，验收状态见[当前记录](../archive/reports/2026-10-20-conversation-tools.md)；P2 已完成本地验收的[只读引用恢复](../archive/reports/2026-10-20-conversation-recovery.md)，自然语言配置仍待后续。用户希望把命令内化到对话、同时容纳小任务和长期项目；本文说明具体行为与后续实施条件，**不表示自然语言路由已完成实现**。源码核对基线为 PR #60 `14a1164`。

## 1. 已有基础与缺口

| 能力 | 当前事实 | 还要补什么 |
| --- | --- | --- |
| 对话调用能力 | [原生扩展](../extensions/pi-sparkle/index.ts) 已注册模型可调用的只读 `sparkle_delegate`，以及需要宿主事先签发句柄的 `sparkle_apply_candidate` | P1 配置后增加查询/焦点/宿主授权直接任务工具；项目推进与新增授权表达仍需后续切片 |
| 普通开发任务 | 实验性 [startDevelopmentTask](direct-development-task.md) 复用 NativeWriteSession，无需项目队列、planner 或金额表单 | 宿主自动装配受信任 executor、检查命令和任务上下文；当前用户仍不能仅凭一句话自动调用所有能力 |
| 长期项目 | [WorkItemStore](../src/development/work-item-store.ts)、[DevelopmentController](../src/development/controller.ts) 已负责依赖、认领、检查和进展 | 对话焦点绑定、跨会话恢复提示、范围受控的计划修改 |
| 长期上下文 | 事件、候选记录、Git、偏好等基础可复用 | 带来源的任务摘要、纠正与失效、按焦点检索；聊天窗口本身不替代项目事实 |

CLI 保留为脚本、排障和高级入口。对话与 CLI 调同一应用能力，不能产生两套行为。自然语言应转换为有结构的操作请求，由宿主解析具体对象、检查权限并调用函数；不把用户原话直接拼成 shell 命令。现有 `issue-candidate` 是宿主操作，不能因为包装成对话就交给模型自行签发。

## 2. 一条消息怎样变成行动

由当前对话模型结合已有焦点理解消息，优先复用已有工具选择，不为每句话强制追加分类模型或规划 agent。

1. **判断话语作用**：问答、查看进度、执行任务、纠正要求、切换/暂停/继续、对具体行动的授权。疑问句也可能是执行意图，需要结合上下文。
2. **解析对象**：显式点名的项目/任务优先，其次是当前有效焦点与消息来源引用。焦点有版本，过期工具结果不能覆盖新焦点；任务 ID 来自宿主事实，不由模型随意编造。
3. **选择已有能力**：直接回答、只读查询、单任务执行、项目队列推进或提出计划修改。任务大小主要决定是否需要持久依赖和跨期协作，风险与外部效果决定检查强度。
4. **宿主校验后执行**：验证路径、工作区、候选、已有授权和当前 revision。检查器来自宿主受信任配置。缺少检查能力就报告缺口，不能让 worker 生成自己的通过判据。
5. **回传实际结果**：展示做了什么、检查结果、未解决点与下一步。引用真实 run/工作项/收据；运行结束、任务接受、源码集成仍是不同事实。

| 用户说法 | 建议动作 | 关键条件 |
| --- | --- | --- |
| “看看目前做到哪了” | 聚合当前项目只读事实 | 不创建任务，不触发执行，不把未知状态计为成功 |
| “把这个按钮的文字改一下” | 直接任务 | 继承当前明确项目与已授权范围，无强制队列或预算提问 |
| “继续昨天的插件开发” | 查找项目记录、候选与阻塞，选择下一可执行项 | 一项明确目标可直接继续；多个合理目标时才询问是哪一个 |
| “刚才那个方案先不要做” | 更新该任务要求；需要时取消受影响运行 | 接到停止请求不等于效果已结束；未决写入继续保留所有权 |
| “把这个候选应用到当前分支” | 将真实用户授权交给宿主解析并绑定精确候选，再调用已有应用能力 | 宿主核验候选/基线/授权，模型不能用自己的复述签发句柄；已有充分授权不重复确认 |

资料、检索结果和插件诊断只能作为证据，不能冒充新的用户指令。低置信度的可逆只读步骤可先推进；会改变目标、跨项目或产生不可逆效果的歧义必须先消除。是否需要确认取决于缺失的事实或授权，不取决于命令原先有多长。

## 3. 同一段对话，连接多个任务

用户可以一直使用一个窗口。系统内部区分三个层次：

| 层次 | 保存什么 | 不承担什么 |
| --- | --- | --- |
| 对话与焦点 | 消息引用、当前项目/任务指针、暂停的主线、待回答问题 | 不再存一份任务完成状态或 apply 权限 |
| 当前任务 | 目标、范围、相关资料、改动与检查引用；项目项走已有 WorkItemStore，临时直接任务沿用 run/native artifacts | 不要求每个问答、小修改都建项目和队列 |
| 长期项目 | 目标、依赖、决策、工作项、阻塞及代码事实的链接；状态复用已有权威记录 | 不把整个聊天历史当作唯一计划，不创建竞争性的 ProjectState |

**插问**只生成回答，例如“顺便解释一下模型路由”，不会替换当前开发任务。
**新增小任务**获得单独的工作上下文，结束后保留原主线的恢复入口。
**纠正**默认绑定被纠正的那项任务；只有用户明确提出长期偏好时才更新长期默认。
**项目推进**按当前依赖和事实找下一项工作，不能因为一句“继续”把所有积压事项并行启动。

焦点指针可以持久化以便跨天定位，但它只是查找入口。恢复前重新读取工作项、效果收据与源码版本；若原任务已完成，就展示结果并找下一步，不能重复执行。重新开一个聊天也应能通过项目事实继续工作，不依赖原模型会话还活着。

## 4. 一段真实的衔接示例

| 这轮消息 | 对话处理 | 原有主线 |
| --- | --- | --- |
| “继续开发插件系统” | 找到插件项目，进入当前可执行的贡献接口任务 | 绑定该任务，展示当前下一步 |
| “顺便把宣讲改成白天模式” | 识别为同项目的一项局部 UI 工作，建立临时焦点并关联原消息 | 保留插件任务指针；重叠写入需先等待/停止并对账，界面切换不释放写入权 |
| “为什么插件不能直接改数据库？” | 在当前对话中解释架构边界 | 问答不修改任何项目工作项的完成状态 |
| “好了，继续插件那部分” | 用显式对象回到插件任务，读取最新源码与证据 | 从已验证的位置继续，不重复白天模式改动 |
| 第二天：“继续这个项目” | 读取进展摘要和底层事实，说明已完成/阻塞/下一步 | 若多个项目都合理，问一个简短的对象选择问题 |

“顺便”不一定意味着独立任务，也不一定意味着可以并行：先判断是否是当前任务的范围内修正；独立目标才另建上下文。同一候选范围仍保持一个写入 owner。隔离且已授权的工作可推进；不能靠切换对话标签绕过未决效果。

## 5. 上下文如何随长线工作保持清晰

每轮按需组装：当前明确要求与授权 → 当前项目目标/有效决策 → 当前任务及候选事实 → 最近相关对话 → 必要源码/检查证据。其余历史可检索，不整段反复塞给模型。

摘要记录“确认的事实、已接受决策、未完成项、待决问题、来源及适用范围”。保持未知和冲突；摘要中的“已完成”必须能回查实际记录。用户纠正、源码/检查定义变化时使相关摘要失效；旧摘要不能覆盖更新的指令。跨项目材料需明确相关性和读取权限，项目 A 的临时要求不进入项目 B 的默认偏好。

目标、权限、验收条件等必需事实不能因压缩被悄悄删掉。应用内部可以管理上下文容量和默认成本提醒，不要求用户为每句话填预算。最小方案使用现有事件/文档引用与词法检索，不强制新增向量库、多 agent 或周期全项目分析。

小任务需要跨天跟踪、依赖其他任务、多人交接或用户明确要求纳入计划时，才提升为项目工作项：引用已有 run/候选，补足工作项定义和检查要求；既有结果不会因此自动获得工作项验收，更不能重跑已产生的外部效果。反过来，项目中的解释和局部询问也不必成为正式工作项。

## 6. 实施顺序与验收

| 切片 | 实施内容 | 可观察验收 |
| --- | --- | --- |
| C1 对话能力入口 | 封装只读状态和已授权直接任务，宿主装配配置 | 日常句子触发正确能力；无需命令参数；不支持的请求明确说明；未授权签发被拒绝 |
| C2 焦点与插问 | 消息到项目/任务的带版本引用、主线恢复 | 连续插问不丢目标；歧义“继续”不误启动；迟到结果不串任务 |
| C3 长期恢复 | 事实引用、摘要失效、按任务检索和跨会话恢复 | 重开聊天能恢复；旧证据不会被当成当前事实；跨项目偏好不泄漏 |
| C4 项目增强 | 任务提升、计划修改、受控自然语言应用授权 | 不重复执行/计入结果，不生成第二套成功状态；源码变化后重验；未知效果不放行 |

这些是建议实施切片，不是本次已运行的测试。与 [M1 轻任务、M3 动态纠偏、M6 项目推进](architecture-migration.md) 对齐；复用现有模块和 [A1/A3/A9](architecture-algorithms.md) 的约束。首轮优先 C1/C2，再用真实长线对话验证 C3/C4，不把全部记忆与调度能力设为日常使用的前提。

P2 的精确实现边界见[恢复计划](../archive/superpowers/plans/2026-10-20-conversation-recovery.md)：显式宿主引用、fresh facts 与新焦点 generation；恢复实例不获得执行权限，不自动重放，队列与直接任务的身份映射分别声明。当前验收以[恢复记录](../archive/reports/2026-10-20-conversation-recovery.md)为准。

# Exploratory A/B/C pilot implementation and evaluation plan

> Draft only. No live run may begin until the preregistration, read-only
> evaluator manifest, Stage 0 boundary review/freeze, budget, and data-transfer
> gates are approved. No product code or retry implementation is part of this
> documentation slice.

## Goal and arm identity

Estimate the marginal economic and behavioral effect of native observation
projection under a frozen, task-paired pilot without making an overbroad outcome
claim.

- **A:** native Pi single-agent baseline, sparkle learned routing disabled.
  A's actual native runtime identity, auth path, and tool schema are frozen
  independently before collection.
- **B:** pi-sparkle with the common frozen routing tuple and projection off.
- **C:** the same B common tuple with projection on. C's recall tool is a
  declared tool-schema difference, not a claim that A/B/C have identical tool
  schemas.

The A source configuration to freeze is the current native path: a separate
`PiAgentExecutor` created by `createNativeExecutor`, host-resolved auth, only
`sparkle_read_file` from the native coding-tool set, and no recall tool unless
projection is supplied. This is a source fact to bind independently, not a
promise that B/C use the same runtime or schema.

Common evaluator, task-set, repository-revision, data-transfer, retention, and
budget constraints are shared. Each arm has its own manifest and
`armManifestDigest`; every ledger row carries that digest.

## Identity and gate

- Owner: experiment owner/evaluator; no live call is authorized by this draft.
- State: `draft — exploratory pilot, not preregistered`.
- Dependencies: projection hardening, the read-only evaluator manifest, and the
  Stage 0 evaluator/apply boundary design review/freeze.
- Refusal rule: any manifest, identity, evaluator, routing, or data-transfer
  mismatch stops the affected collection and records `INVALID_COLLECTION`; it
  is never silently repaired or relabeled as a model failure.

## Fixed schedule and actual retry scope

- Approximately 30 distinct real development tasks are fixed before outcome
  inspection. Every task is scheduled in A, B, and C unless an incomplete-block
  rule is approved in advance.
- Exactly **K=2 scheduled runs per task per arm** are attempted. No
  outcome-driven extra task run, favorable-arm rerun, or post-outcome replacement
  is allowed.
- `taskAttemptsPerScheduledRun=1` is a preregistered scheduled-run field. This
  documentation does not implement or claim enforcement of task retry policy;
  any observed mismatch is declared and blocks collection.
- The existing provider executor has a local `maxAttempts=3` upper bound per
  `PiAgentExecutor.execute()` execution, including the first attempt. It is a
  retry upper bound, not exactly three provider API calls and not a global budget
  across children or tool turns. Only the provider executor path that actually
  applies is counted. Provider failures, retry timing, and all observed costs
  stay inside the scheduled-run ledger row.

## Canonical estimands

```text
costPerAcceptedTaskBundle(arm) =
  sum(providerCost + runtimeCost across both scheduled runs and applicable
      provider-executor retries)
  /
  count(distinct tasks with >=1 valid independently accepted run without
        human correction)
```

A zero denominator is undefined and blocks a claim. Secondary metrics include
cost per accepted run, independent acceptance rate, correction minutes, wall
time, retry/failed-attempt counts, repeat mass, integrity incidents, and an
all-in human-time sensitivity. Missing usage is unknown, never zero.

The primary contrast is B→C, conditional on the frozen equivalence manifest.
A→B is a system-level contrast, not a pure projection effect.

## Run states and missingness

Each scheduled run is one of:

`ASSIGNED_NOT_STARTED`, `STARTED_PROVIDER_FAILURE`, `RUNTIME_FAILURE`,
`EVALUATOR_FAILURE`, `VALID_COMPLETED_ACCEPTED`,
`VALID_COMPLETED_REJECTED`, `CANCELLED`, or `INVALID_COLLECTION`.

Provider/auth/quota/timeout/runtime failures contribute all observed cost and
zero operational acceptance. Evaluator/manifest failures are
`INVALID_COLLECTION`, not model failures; their reason and cost remain in the
ledger. No run is replaced or excluded after outcome inspection. A reserve task
may replace only a predeclared invalid collection before outcome inspection,
while the original remains.

Unknown required provider/runtime cost makes the affected arm's point estimate
`UNKNOWN_COST`; report known-cost lower bounds separately. Operational failures
remain paired zero-acceptance observations. Invalid-collection handling must be
frozen before collection; no favorable exclusion is permitted.

## Preregistration rules

Freeze before collection and before outcome inspection:

- task/repository revisions, strata, task set and confirmation set;
- K=2, A/B/C assignment, randomized arm/repeat order and concurrency;
- A native configuration and B/C shared tuple, including runtime/tool identity
  fields and the declared C recall-tool difference;
- provider/model/version, timeout, cancellation, cache/session policy where
  exposed, and the applicable local retry upper-bound scope;
- evaluator manifest and `boundaryDesignDigest`;
- missingness, invalid-collection, reserve-task, and stopping rules;
- paired task-clustered bootstrap or hierarchical estimator, interval, and MDE;
- budget, retention, and data-transfer policy.

## Acceptance criteria

- [ ] Manifest and preregistration digests are frozen before the first live call.
- [ ] A's native configuration is independently frozen; any mismatch blocks
  collection. B/C share the frozen common tuple; C's schema difference is
  explicit.
- [ ] Exactly K=2 scheduled runs per task/arm are attempted. The planned
  task-attempt field is 1; the existing provider executor's maxAttempts=3 is
  recorded as a local upper bound per execute, not an exact API-call count or
  global child/tool-turn budget. No outcome-driven extra runs occur.
- [ ] Every result and ledger row includes the common manifest digest and
  `armManifestDigest`, with provider/runtime/evaluator failures and unknown
  usage retained.
- [ ] Primary and secondary estimands use task-level clustering; repeats are not
  independent tasks; zero accepted and unknown-cost cases use the frozen rules.
- [ ] The pilot report does not claim non-inferiority, F6 closure, live adaptive
  benefit, production readiness, or broad Outcome-supported benefit.

## Problem and scope

The repository uses SHA-256 both as a cryptographic content/integrity mechanism and as a persisted/wire identifier. Removing it is not a rename: it affects content addressing, artifact lookup, independent verification, worktree fingerprints, observation dedupe, holdout commitments, migration, apply handles, tests, privacy paths, and active evaluator contracts.

The evidence-first census was run against the pre-edit tree at revision `45dbb0e9c40e5c75393206ca3b21a44b50bafeae`. It found:

- 219 first-party matching files and 836 matching lines;
- 65 direct SHA-256 computations;
- 778 persisted or wire references;
- 45 validation/integrity references;
- 1,418 identity/cache/dedupe-related matches;
- 37 runtime-scope files: 16 source files, 17 tests, 3 scripts, and 1 extension.

Raw, non-secret census artifacts are retained under `.agent_workspace/remove-sha256/`. Existing dirty and untracked content is preserved; no runtime state, credentials, provider call, experiment, deletion, reset, commit, push, merge, or apply operation is part of this slice.

### In scope for this bounded slice

### Explicitly out of scope

- Rewriting historical reports, archived plans, sealed F6 materials, or old evidence to erase what was used.
- Selecting a replacement cryptographic hash.

## Execution boundary and non-substitution rule

This request means removal of SHA-256 mechanisms and runtime checks. It does not mean renaming `sha256` fields, changing only the displayed algorithm name, or substituting another cryptographic hash. The user accepted removal and delegated implementation to Luna. Where an ID is needed, use opaque random versioned locators; where equality/dedupe is needed, compare exact bytes directly. This provides no cryptographic tamper guarantee. Legacy records are never silently reclassified. Migration/live-provider/production-apply and other experimental/production gates remain separate. The current slice does not change persisted wire schemas.

## Dependency-ordered follow-on implementation

### Stage 0 — accepted removal contract

1. ADR-008 is accepted for removal and implementation.
2. No replacement cryptographic hash is selected: IDs use opaque random versioned locators where needed, and equality/dedupe uses exact byte comparison where needed.
3. Freeze versioned schemas only in later migration groups; this `migrate-legacy` slice does not change persisted wire schemas.
4. Legacy records remain historical/read-only and are never silently rehashed, upgraded, or reclassified.

### Stage 1 — pure identity and storage surfaces

Migrate observation and loop-artifact storage first, including filenames, refs, validators, placeholder text, lifecycle/privacy paths, and all unit/integration fixtures. Preserve run scoping, symlink refusal, quotas, locking, deletion, and snapshot-after-write semantics. A legacy ref must not resolve through a new lookup path.

### Stage 2 — execution evidence and worktree binding

Migrate `worktree-snapshot.ts`, `independent-check.ts`, `acceptance.ts`, `closed-loop.ts`, and native write/apply plumbing as one contract. The apply path must refuse legacy artifacts/handles before mutation. Re-pin candidate identity, command/argv, revision, before/after tree state, and crash rollback behavior with negative tests.

### Stage 3 — experiment, migration, and ledger identity

Migrate freeze/task-spec/holdout/custody scripts, observation-ledger identity, and legacy migration. Existing sealed artifacts remain historical and cannot be re-sealed in place. `migrate-legacy` comparison equality uses exact bytes only; this slice does not change persisted wire schemas or authorize migration execution. Remaining Stage 3 surfaces require their own test-first slices and separate experimental/production gates.

### Stage 4 — active documentation and contract sweep

Update data dictionary, evaluator boundary/manifest, projection plans, F6 active specifications, status rows, task records, and public descriptions. Historical evidence remains unchanged except for additive supersession notices. Acceptance requires no active normative SHA-256 dependency outside the explicit legacy-compatibility section.

### Stage 5 — removal gate

Run focused tests for each stage, then `pnpm gate`, security and Pi probes, compatibility/migration probes, and the full active-contract scan. A failed legacy refusal, changed default-off behavior, changed privacy cascade, or unbound evaluator/apply identity aborts the migration.

## Compatibility and fail-closed policy

- **New data:** must use the new versioned successor schema after Stage 0; no dual-write is allowed unless explicitly approved because it prolongs the old mechanism.
- **Legacy data:** SHA-bearing records are not silently upgraded, rehashed, or treated as equivalent. Readers may inventory and report them as `LEGACY_SHA256_UNSUPPORTED`; they must not classify them as trusted, applyable, evaluable, or fresh.
- **Legacy handles/artifacts:** apply, disposal, evaluator, and migration mutation paths refuse before side effects. The refusal names the required migration record, not secret or raw runtime content.
- **Historical evidence:** remains immutable evidence of the old design. It is excluded from the active-removal acceptance scan but linked from the report.
- **Holdout/F6:** sealed commitments are not rewritten. Any future run requires a new seal version and owner/F6 approval; no experiment is run by this task.
- **Privacy:** no scan or report copies credentials, auth files, provider transcripts, or raw runtime records. Existing retention/deletion semantics remain unchanged until their stage is implemented and tested.

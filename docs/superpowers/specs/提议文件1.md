# 提议文件1：三线追踪与路由方案的外部证据综合评估

日期：2026-08-18 之后的外部审核整理
状态：提议，不替换已冻结定稿，不授权实现或上线
适用范围：`2026-08-18-three-line-tracking-定稿.md`、`2026-08-18-three-line-tracking-design.md`、ADR-004、Checkpoint F

## 1. 执行摘要

原方案的主方向成立：执行、追踪、分析应隔离；运行时不能自行修改活跃提示、权限、评分表或路由；分析只能产出候选；候选必须经过版本化、回放、影子/金丝雀、用户批准和 CAS 回滚；高风险路径不能在线探索。

外部开源项目和论文进一步支持这些边界，但没有支持原方案把 `P/H/score` 直接变成路由成功率，也没有支持在当前数据条件下立即启用复杂的模型/项目/交互归因。我的最终判断是：

1. **§1–§9 可以保留为产品方向，但必须补成事件、状态转换和信任边界的实现规格。**
2. **生产控制权应收敛到现有 M2 deterministic supervisor，而不是新增一个会与 supervisor 竞争的独立 GateController 服务。** Tracking 只产生结构化 assessment；supervisor 按固定规则决定重试、阻塞、询问用户或排队分析。
3. **`score` 只能是分析唤醒信号，不能是 routing outcome。** 生产 R1 应继续使用有明确来源的 `PASS/FAIL`，并把任务成功、策略合规、用户接受、成本/延迟作为不同结果维度。
4. **当前 §10.2 的“层级 Beta-Binomial”名不副实。** 它是概率尺度上的嵌套经验收缩启发式，不能同时声称是一个联合共轭生成模型。它应从 live router 中移出，先作为离线研究估计器；生产先保留现有单层 R1，并修正 LCB、先验样本和回退规则。
5. **RouteLLM、FrugalGPT 等工作支持“校准过的质量/成本操作点”和级联回退，不支持在本项目缺少稳定标签时凭稀疏后验自动换模型。** Checkpoint F 的 paired holdout 或有效 OPE 仍是唯一可称为 Outcome-supported 的入口。
6. **隐藏 CoT 不应进入异常包。** 异常分析应使用工具事件、公开理由、证据和可审计短摘要；隐藏推理既不持久化，也不成为回放依赖。

建议把冻结状态改成：

> 三线和评分门控为“待实现规格”；路由 §10 为“离线研究与实验规格”；生产动态路由保持关闭，直到 Checkpoint F 的实验协议、结果指标和回滚条件全部关闭。

## 2. 证据范围和证据等级

本提议区分三类内容：

- **项目机制事实**：官方文档或源码明确实现的机制，可以借鉴工程形状，但不能自动证明本项目效果。
- **论文结果**：论文在其数据、模型和任务上的结果，只支持相同条件下的研究假设，不直接证明 `pi-sparkle` 的收益。
- **设计推断**：结合本仓库 ADR、代码和外部证据得到的方案，必须通过本地 fixture、回放和 holdout 验证。

关键原则仍以本仓库现有 ADR 和规范为最高优先级：`docs/decisions/0004-controlled-adaptation.md`、`0005-checkpoint-f-holdout-open-questions.md`、`docs/specs/adaptive-agent-work-loop.md` 以及当前可执行测试优先于外部项目的默认做法。

## 3. 外部项目和论文的可借鉴机制

### 3.1 Temporal：确定性工作流、事件历史和回放

来源：

- https://docs.temporal.io/workflow-definition
- https://docs.temporal.io/workflows

可借鉴的机制是：工作流状态由事件历史重建；非确定性或外部副作用被隔离到 activity；状态转换由工作流代码而不是模型自由文本决定；回放是可靠性和版本兼容的重要检查。

对本项目的结论：

- 不新增一个会独立决定运行状态的 LLM GateController。
- 将 Tracking assessment 视为输入事实，将合法状态转换留在 `src/run/supervisor.ts` 的 deterministic supervisor。
- `RETRY_CHECK`、`WAITING_FOR_USER`、`ANALYSIS_QUEUED`、`ABORTED` 等必须是有限白名单转换。
- 每次转换写入 append-only event，并可由 `runId/episodeId/turnId/seq` 重放。
- 分析线的调用属于 adaptation activity，不能直接修改 live supervisor state。
- 如未来出现 schema 或策略版本不兼容，采用显式 versioning/migration，不让模型在运行中自行解释旧状态。

Temporal 不意味着本项目要引入 Temporal 依赖；这里借鉴的是确定性状态机和事件回放原则。

### 3.2 OpenTelemetry：因果链、Span、Event 和上下文传播

来源：

- https://opentelemetry.io/docs/specs/otel/overview/
- https://opentelemetry.io/docs/specs/otel/trace/api/

OpenTelemetry 将 trace 组织为有父子关系的 span，span 可以拥有带时间和属性的 event，并要求跨边界传播可追踪的上下文。

对本项目的结论：

- 每个 run、task、tracking turn、tool call、check、gate decision、candidate evaluation 都应有稳定关联 ID。
- 结构化 tracking event 不应只存一段 summary；应存 `traceId/runId/episodeId/turnId/parentEventId/seq`、来源、版本、时间、证据引用和内容哈希。
- 观测属性和用户/工具正文分开。正文默认引用或加密，不把完整正文作为普通 telemetry attribute，避免秘密泄漏和不可控体积。
- `GateDecision` 必须引用导致它的 event IDs，而不是引用 tracker 的自由文本解释。
- 这能补足原方案中的“工具情况”定义，但不能把 OpenTelemetry trace 当作产品真相；M0–M2 的 immutable run event 仍是 source of truth。

### 3.3 Open Policy Agent：决策日志、决策 ID 和脱敏

来源：

- https://www.openpolicyagent.org/docs/management-decision-logs
- https://www.openpolicyagent.org/docs/latest/overview/

OPA 的决策日志实践强调：每次 policy decision 有稳定 decision ID，可关联请求上下文和决策结果；敏感输入应按策略脱敏或掩码；日志用于审计而不是让策略执行结果变成自由文本。

对本项目的结论：

- R0、权限、路径 ownership、隐私和 high-risk whitelist 应产生结构化 policy decision，包含 `policyVersion`、`decisionId`、输入摘要哈希、结果和拒绝原因。
- 不能只把 `escaped=true` 写入 tracker，然后让 LLM 推断严重性；ownership 判定应由确定性策略完成。
- 用户文本、路径名、工具输出和异常包必须标记为不可信数据，不能被分析模型当成指令。
- OPA 只是可选的外部参考，不建议现在把 OPA 引入 TypeScript 运行时；现有 R0 和 supervisor 已有确定性边界，先复用本地接口。

### 3.4 Inspect AI：评测、Solver/Scorer、日志和沙箱

来源：

- https://inspect.aisi.org.uk/
- https://github.com/UKGovernmentBEIS/inspect_ai

Inspect AI 将任务、solver、scorer、模型和日志分开，支持多轮对话、工具使用、模型评分和沙箱；它把评测配置和结果作为可复查的对象，而不是只保留最终自然语言。

对本项目的结论：

- Tracking、evaluation 和 analysis 应分别建模，不能把 tracker 的 prescore 当 scorer 的任务结果。
- 每个 outcome 必须有 rubric/criterion、evaluator identity、evidence refs 和 abstain 状态。
- LLM judge 只能是 inferential evidence，不能推翻失败测试、权限拒绝或 schema violation。
- 对工具和代码任务，评测必须在隔离工作区/容器中执行；工具 allowlist 不是 sandbox。这与 `m0-m2-architecture.md` 的现有结论一致。
- 可借鉴 Inspect 的“日志可重放 + scorer 可替换”，不应默认给每一轮额外调用 judge LLM。

### 3.5 SWE-bench：容器化、最终变更集和缓存隔离

来源：

- https://github.com/SWE-bench/SWE-bench
- https://www.swebench.com/
- https://arxiv.org/abs/2410.03859

SWE-bench 的公开 harness 使用 Docker 进行更可复现的评测，并把 build/run/evaluation 结果分开保存。其文档还警告缓存按 `run_id` 和 `instance_id` 关联；改变预测内容必须改变 run ID，否则可能错误复用旧结果。

对本项目的结论：

- candidate replay 必须绑定 `candidateVersion + episodeId + evaluatorVersion + environmentHash + runId`，不能只按 task ID 缓存。
- 最终验证必须绑定最终 artifact/diff hash，而不是绑定某个早期草稿。
- replay、shadow、holdout 使用只读原始事件和隔离 workspace，禁止回写生产 episode。
- 静态 holdout 可能过时；已有仓库研究记录的 SWE-bench Live 证据说明需要冻结可比 split，同时周期性轮换新 holdout，并标记被优化污染的 holdout。

### 3.6 lm-evaluation-harness：公开配置、可比指标和 decontamination 意识

来源：https://github.com/EleutherAI/lm-evaluation-harness

该项目强调公开 prompt/task 配置、统一模型接口、多个指标和可重复运行。对本项目的启示是：实验卡必须公开 evaluator/rubric/version、数据 split、随机种子、模型版本、成本计算和指标定义；不能只报一个平均分。

### 3.7 MLflow Model Registry：版本、lineage、alias 和回滚

来源：https://mlflow.org/docs/latest/ml/model-registry/

MLflow 的 registry 通过不可变版本、lineage、tags 和可变 alias 管理生产指针。alias 可以指向某个具体版本，重新绑定 alias 即可切换生产版本；版本 metadata 记录验证状态和来源。

对本项目的结论：

- ADR-004 的 immutable resource version、content hash、parent lineage、active pointer 和 CAS 方向是正确的。
- `routing-policy` 必须是版本化候选，不允许在现有对象上修改权重。
- active pointer 更新必须携带 expected parent/version、approval profile、promotion evidence 和 rollback target。
- 借鉴 alias 的便利，但保留本项目更严格的 append-only promotion ledger 和 CAS，不把 mutable pointer 当成审计记录本身。

### 3.8 FrugalGPT：级联和成本/质量操作点

来源：

- 论文：https://arxiv.org/abs/2305.05176

FrugalGPT 的核心是多模型级联：先尝试成本较低的模型，依据门控/置信信号决定是否升级，从而在成本和质量之间选择操作点。

对本项目的结论：

- “过质量线的最便宜模型”是合理的生产目标，比永远选择最高平均分更符合成本控制。
- 但 FrugalGPT 的实验不是本项目数据的证明；这里的 gate 必须用本地确定性检查、已校准质量估计和风险分层实现。
- fallback 必须是批准的保守 baseline，不应在所有模型都稀疏时依据噪声最大的最高 LCB 临时选择。
- 高风险任务不探索；必要时直接固定到批准模型或升级并等待用户。

### 3.9 RouteLLM：偏好数据、路由器阈值和校准

来源：

- 论文：https://arxiv.org/abs/2406.18665
- 项目：https://github.com/lm-sys/RouteLLM

RouteLLM 使用偏好数据训练路由器，在强/弱模型之间作选择，并用 cost threshold 控制操作点。官方 README 明确建议按实际查询分布校准 threshold；公共 Chatbot Arena 数据并不自动代表新项目的 query distribution。

对本项目的结论：

- 可以借鉴“路由器不是一个隐式权重，而是一个有版本、可校准的 operating point”。
- 可以借鉴 pairwise preference、匿名化、threshold calibration 和多 benchmark evaluation。
- 不能直接使用 RouteLLM 的公共 preference router 作为本项目多角色、多项目、多风险模型簇的 live router。
- 本项目当前没有足够稳定的 pairwise 或绝对任务成功标签，先不引入 learned router。
- 若未来尝试 RouteLLM 类方法，必须与当前 R0/R1 做 sealed holdout、校准、成本和 guardrail 比较，而不是只比较 AUC。

### 3.10 Doubly Robust OPE：反事实评估的必要条件

来源：Dudík、Langford、Li，`Doubly Robust Policy Evaluation and Learning`：
https://arxiv.org/abs/1103.4601

该工作说明，历史策略下只观察被选择动作的结果时，新策略的评估需要 outcome model、logging policy/propensity，或二者结合；没有动作覆盖时，反事实结果不能凭空恢复。

对本项目的结论：

- “always log exposure”是必要条件，但仅记录 exposure 不等于有有效 OPE。
- 每个 eligible action 需要记录选择概率/propensity、策略版本、拒绝原因、上下文版本和可用动作集。
- 必须报告 overlap、propensity clipping、effective sample size、估计器和置信区间。
- 未调用的 shadow 模型没有结果标签；只能增加 exposure，不能假造反事实 outcome。
- 优先采用 paired isolated evaluation；只有在 paired 不可行且 overlap 合格时才使用预注册 DR/IPS 方案。

### 3.11 LLM-as-a-Judge、Chatbot Arena 和成对比较

来源：

- MT-Bench/LLM-as-a-Judge：https://arxiv.org/abs/2306.05685
- Chatbot Arena：https://arxiv.org/abs/2403.04132

相关研究记录了位置、冗长、自增强和 judge 偏差；Chatbot Arena 使用匿名随机成对偏好和 Bradley–Terry 类估计。

对本项目的结论：

- 用户明确选择的 pairwise preference 可作为 `user_acceptance` 或 `relative_preference`，不能直接当作绝对 correctness。
- consequential comparison 要盲化模型身份、随机 A/B 顺序、交换展示顺序，保留 disagreement 和 abstention。
- judge 必须按 criterion 校准到人工或 deterministic outcome；不能由 actor 自评和同家族 judge 共同证明自己的路由价值。
- 这支持原方案的 evidence precedence，但也说明 `H` 不应被混进模型任务成功率。

## 4. 对原方案和上一版建议的再评价

### 4.1 原方案中应保留的决定

- 三线隔离和 analysis 不修改 in-flight run。
- rolling summary 只供 tracking 下一轮消费，execution 不把 summary 当 authority。
- `UNOBSERVED` 不填 0.5。
- hard gate 优先于 soft threshold。
- 权限、安全、凭据不自动晋升。
- R0 硬过滤、high-risk no-exploration、shadow-only bandit。
- candidate version、evidence、rollback target、CAS promotion。
- paired/holdout/OPE 作为 Outcome-supported 的前提。

这些决定与 Temporal/OPA/OTel/MLflow/Inspect/SWE-bench 的工程实践一致。

### 4.2 上一版建议需要修正的地方

我上一版提出“新增 GateController”作为概念澄清，但结合当前仓库后应修正为：**不新增竞争 authority；由现有 M2 deterministic supervisor 承担 gate application，Tracking 只负责 assessment。** 这是更小的架构变化，也符合 `src/run/supervisor.ts` 已有的 ledger、lease、合法状态转换和 replay 结构。

我上一版建议把 P 设为“加权质量 × 观察覆盖率”可以作为一种实现，但不应把它解释成任务质量。更稳妥的定义是：P 是 tracking credibility，维度值和缺失规则固定，coverage 只反映“本窗证据覆盖程度”，硬失败直接走 gate。Narrative coherence 保留为诊断字段，不参与 P。

我上一版建议的层级 logistic 模型仍然只适合离线研究，不适合当前 TypeScript live path。它需要明确 outcome 定义、版本/时间协变量、随机效应先验、拟合/收敛、校准和失效降级。当前应先使用已有单层 R1，避免为了解释 attribution 而引入一个没有本地数据支撑的复杂依赖。

我上一版建议把 `n_obs_eff` 与 `n_prior_eff` 分开，应立即采用。现有 `src/routing/posterior.ts` 的 `weightedSampleSize` 已从 prior 中扣除，这是正确方向；promotion gate 仍要显式检查目标 cell 的真实/衰减后观察量，不能依靠 posterior 总强度。

## 5. 收敛后的目标架构

### 5.1 权威边界

```text
Execution
  -> immutable M0-M2 run events
  -> deterministic supervisor / ledger

Tracking
  -> reads event facts + current window
  -> emits TrackingAssessment + RollingSummary
  -> never emits free-text authority

Supervisor
  -> validates assessment schema and evidence references
  -> applies fixed state transition table
  -> may issue only allowlisted bounded directives

Analysis
  -> reads sanitized anomaly packet
  -> emits typed ImprovementCandidate
  -> never writes active resources or in-flight run state

Promotion
  -> validates candidate evidence and approval profile
  -> CAS updates active pointer
  -> append-only promotion/rollback ledger
```

Tracking 的 assessment 可以让 supervisor 知道“应重跑一次检查”“应询问用户”“应排队分析”，但 assessment 本身不具有命令权。每个 directive 必须由 supervisor 根据代码中的 gate decision 生成，而非由 tracker prose 生成。

### 5.2 最小状态机

建议固定为：

```text
RUNNING
  -> REPAIRING          bounded deterministic repair only
  -> WAITING_FOR_USER   authority, security, ambiguity, or fail-closed omission
  -> ANALYSIS_QUEUED    hard/soft anomaly packet persisted
  -> COMPLETED          required outcome evidence present
  -> ABORTED            explicit stop, unrecoverable policy violation
```

每个转换需记录：

- `transitionId`, `runId`, `episodeId`, `turnId`, `seq`；
- `from`, `to`, `reasonCode`；
- `assessmentHash`, `evidenceRefs`, `policyVersion`；
- `idempotencyKey`、actor class（system/user，不用 actor self-defense）；
- expected state/version，用 CAS 防止并发 tracking turn 重复转换。

`REPAIRING` 只能调用预注册的 repair operation，例如重跑一个已知检查；不能改变计划、权限、工具集或 active resource。

### 5.3 事件和 summary

建议把当前 `OperationRecord` 扩展为可验证事件，而不是让 summary 承担所有事实：

```text
Event:
  schemaVersion, eventId, traceId, parentEventId, runId, episodeId, turnId, seq
  eventType, occurredAt
  source: EXECUTION | TRACKING | SUPERVISOR | ANALYSIS | USER | DETERMINISTIC_CHECK
  trust: FACT | DERIVED | INFERENTIAL | UNTRUSTED_TEXT
  policyVersion, contractVersion, modelVersion
  target/scope, exitCode, durationMs, write/escape flags
  evidenceIds, artifactIds, contentHashes
```

Rolling summary只保留下一轮 tracker 所需的结构化索引：活动约束、未决事项、操作引用、当前 assessment、open-minors、omissions 和 summary hash。它不复制全部正文，也不进入 execution context。

任何 omission 必须有 `omissionKey/reason/mandatory/sourceEventIds`；mandatory omission 直接触发 fail-closed。摘要采用原子 append，带前一摘要 hash，避免中途崩溃后出现无法解释的断链。

### 5.4 异常包和提示注入

异常包默认包括：

- 结构化 summary；
- 当前窗口工具 situation、事件 ID、退出码、hash、证据引用；
- P/H/score 和 gate code；
- 被引用的必要 artifact 的安全片段。

默认不包括隐藏 CoT，也不建议在异常时读取隐藏 CoT。若确实有 provider 提供可审计的公开 rationale，字段标记为 `INFERENTIAL`；工具正文按最小授权、脱敏和引用读取。

用户文本、工具正文、路径名、模型输出都标为 `UNTRUSTED_TEXT`，包装成数据而不是系统指令。分析 prompt 必须明确：这些内容只能作为证据，不能要求它改变 authority、读取新资源或执行工具。

## 6. Tracking 评分的可执行化

### 6.1 P 的定位

`P` 只回答：“本窗 tracking 对过程事实的可信度有多高？”不回答：“模型完成任务的概率是多少？”不回答：“用户喜欢不喜欢模型？”

每个维度输出 `PASS/FAIL/UNOBSERVED/NOT_APPLICABLE` 和 evidence refs。建议使用以下固定维度：

| 维度 | 推荐判定 | 是否可 hard gate |
| --- | --- | --- |
| evidence consistency | claims 与事件、退出码、artifact/hash 一致 | 是 |
| scope safety | ownership、路径规范化、符号链接和 policy decision 通过 | 是 |
| check coverage | required checks 全部有真实 check event | 是 |
| constraint retention | mandatory constraints 都在当前摘要或可引用事件中 | 是 |
| progress | 有新 artifact、状态变化或新证据 | 重复失败时是 |
| narrative coherence | 只做诊断，不进 P | 否 |

推荐 v1 公式：

```text
applicableWeight = 适用维度的固定权重总和
observedWeight   = PASS/FAIL 维度的权重总和
quality          = Σ(weight * value) / observedWeight
coverage         = observedWeight / applicableWeight
P                = round(quality * coverage, 4)
```

`NOT_APPLICABLE` 不进入分母；`UNOBSERVED` 不被填成 0，但会降低 coverage。无可观察维度时 `P=0`。hard-related FAIL 仍直接触发 hard gate，并可把 P cap 在 0.30 作为诊断显示。权重必须版本化，不允许 tracking 模型学习权重。

这比“所有维度简单平均但缺失不清楚”更可重算；但 P 仍只是分析门控分，不得进入 routing outcome。

### 6.2 H 的严格边界

保留 ratio -> ten-point -> short-rule 的顺序，但增加以下规则：

- ratio 只接受稳定 item ID 和明确 agreed/rejected 状态；evaluable=0 返回 UNOBSERVED；
- 评分范围限制在 0–10；多个无明确指向的评分返回 UNOBSERVED；
- `permission/security/stop/rollback` 先进入 hard gate，不被整体 ratio 抵消；
- 沉默、`ok/行/继续` 和只补充要求不产生 H；
- 同一回复一次只允许一个最高优先级处理路径，hard reject 优先于 score；
- 不做“情绪检测”，不把用户修改、沉默或点击隐式解释成偏好。

### 6.3 score 的唯一用途

原 `score = P` 或 `0.7*min(H,P)+0.3*max(H,P)` 可保留为版本化 analysis gate，只要明确：

- hard gate 先判断；
- `score < threshold` 只表示需要分析，不表示模型任务失败；
- 它不得写入 `OutcomeObservation` 的 PASS/FAIL；
- `H` 的用户接受度单独落盘为 `user_acceptance`，其 provenance 和 scope 单独记录。

### 6.4 minor

为 minor 定义稳定 key：

```text
minorKey = hash(ruleCode, normalizedTarget, constraintId)
```

“连续两轮”指相同 minorKey 在相邻 tracking turns 仍为 verified-true；“累计三条”按 episode ledger 中未关闭的 key 计算。只有新事件、hash 或 deterministic check 能关闭 minor；tracker 自己的再次叙述不能关闭它。

## 7. 路由方案的最终优化

### 7.1 先拆结果，不再使用 score 作为 y

至少保存以下独立结果向量：

```text
taskSuccess       = 独立任务验收/测试/人工明确 correctness
policyCompliance  = 权限、隐私、ownership、契约和工具策略
userAcceptance    = 用户显式接受、拒绝、评分或 pairwise preference
cost              = provider cost / tokens
latency           = elapsed and provider latency
rework            = 后续修复、回滚、重复检查
```

生产 R1 初期只优化 `taskSuccess`，`policyCompliance` 是硬过滤和 guardrail；`userAcceptance` 不混入 taskSuccess；cost/latency 作为约束或次级 Pareto 指标。

路径逃逸应触发安全阻断和 policy outcome，但不能自动证明模型不具备任务能力。若产品有意将安全行为纳入可用性，则必须把它明确定义为独立目标，而不是隐式混入 `y=0`。

### 7.2 生产阶段：保留并修正单层 R1

现有 `src/routing/outcomes.ts` 和 `src/routing/posterior.ts` 的单层 Beta-Bernoulli R1 是当前最可审计的生产基线：按 `(taskFamily, role, modelVersion, featureVersion)` 聚合 `PASS/FAIL`，对时间衰减，稀疏时回退 R0。

应做的改进：

1. `ABSTAIN/UNOBSERVED` 只增加 exposure，不更新 posterior；现有实现已遵守。
2. 显式记录 `observedWeight`、`priorStrength`、`nObsEff`、`nPriorEff`，promotion 只检查 `nObsEff`。
3. `minSamples=5` 只作为 trust/promotion gate，不阻止估计器为稀疏格计算 provisional posterior。
4. LCB 优先改为 Beta 单侧分位数；若暂时保持正态近似，必须标记为 engineering approximation，并增加小样本模拟覆盖率测试。
5. 相同 LCB 的 tie-break 按 R0 的成本/批准顺序，保持确定性；已有 `r1.ts` 的 tier-order tie-break 方向正确。
6. 没有 well-sampled estimate 时，回退批准的 R0 baseline；不要在全体稀疏时选择“最高 LCB”作为 live 结果。
7. 模型版本或 prompt 版本变化时创建新 key、保留旧数据用于审计；不要把旧 model failure 静默归因给新版本，也不要无审计地把 project effect 继承给新版本。
8. 增加 cooldown/hysteresis，避免两个模型在边界附近来回切换。

生产决策：

```text
R0 hard filter
  -> high-risk: approved list only, no exploration
  -> no approved adaptive policy or target nObsEff gate failed: approved R0 baseline
  -> target passes gate and LCB >= quality floor: cheapest passing model
  -> none passes: approved conservative fallback/escalation
```

“最高 LCB”可以作为离线诊断，不应作为稀疏数据下的 live fallback。

### 7.3 离线阶段：真正的联合归因模型

原 §10.2 如果要保留，应改名为“离线层级归因研究”，不要称为闭式共轭 Beta-Binomial。推荐模型形状：

```text
logit Pr(taskSuccess_i) =
  α(scenario, role)
  + u(modelVersion)
  + v(project)
  + w(modelVersion, project)
  + β * time/version covariates
```

要求：

- 所有 outcome 来自同一个 taskSuccess 定义；不要将 P、H、policy failure 混成一列；
- `mp` 观测只能在 interaction 项中使用一次，不能先进入 model/project parent 又再次进入 mp leaf；
- interaction 使用更强收缩，但强度必须作为版本化先验/正则化参数报告；
- 需要明确拟合方法、收敛/失败降级、参数后验或 bootstrap 方案；
- LCB 和 effect interval 使用同一后验/重采样分布，而不是点估计分别拼接；
- `p_m - μ_s`、`p_p - μ_s`、`p_mp - p_add` 的不确定性要传播协方差；
- 只有后验概率/置信度达到预注册标准，才输出 avoid/prefer diagnosis；否则输出 uncertain。

如果项目暂时不愿引入统计依赖，则采用更保守的两阶段方案：

1. 只做场景×模型单层 R1，取消 project/interaction attribution；
2. 项目和交互归因只输出结构化候选，不进入 live routing；
3. 等离线模型、校准和覆盖率报告完成后再恢复归因。

我推荐第二种作为 M3–M6 的默认实现，因为它与现有 TypeScript 代码、测试和 R0/R1 设计最相容。

### 7.4 不能由曝光产生反事实标签

`exposure`、eligible set、reject reasons 和 propensity 必须在 assign 时记录，但：

- 没有调用的 shadow model 没有 outcome；
- bounded repair 能为已调用模型提供新 deterministic label，但不能为未调用模型提供标签；
- shadow replay 只能在隔离环境中重新执行并明确记为 replay evidence；
- OPE 需要 action coverage、propensity overlap、outcome model 和预注册 estimator；
- 不得用“如果按新表会选它”替代真实结果。

## 8. Candidate、分析和晋升

### 8.1 分析输出

分析每次只生成一个明确 resource boundary 的 typed candidate：

```text
candidateId, targetResource, parentVersion, patchHash
hypothesis, supportedEvidence, affectedScopes
metrics, guardrails, evaluationPlan, rollbackTarget
status, risk, approvalProfile
```

候选必须区分 diagnosis、prediction 和 proof。分析可以依据重复结构化 episode signature 提出候选，但不能因为 anomaly 一次出现就断言根因，更不能因为 tracker 自己给了高分就自证。

### 8.2 评测阶梯

沿用并强化现有 adaptive work-loop：

1. static schema/policy/secrets/resource validation；
2. train/validation replay，只读原始事件；
3. sealed holdout，按 episode/time/project 分割并做污染检查；
4. counterfactual shadow 或 paired isolated run；
5. low-risk、固定预算、可回滚 canary；
6. comparable later window；
7. CAS promotion 和自动 guardrail rollback。

每个报告必须包含：evidenceClass（simulation/replay/shadow/paired/production）、数据 split、candidate/parent hash、evaluator/rubric version、成本、延迟、quality vector、policy violation count、CI/credible interval、coverage、失败和 abstain 数量。

### 8.3 Checkpoint F 的具体晋升条件

在现有 ADR-005 基础上补充：

- primary endpoint 是预注册的 `taskSuccess` 或多目标 utility，不使用 score；
- paired isolated evaluation 优先；不可 paired 时才使用有 overlap 的 OPE；
- adaptive 与 R0 的质量差异满足预注册非劣/优效条件；
- 成本差异满足 CI 上界条件，不能只看均值；
- 所有 high-risk/policy guardrail 为零回归；
- 每个决策都能由版本化输入重建；
- 报告校准/ECE、覆盖率、任务族/风险层 breakdown，而非只报 overall average；
- 未达到条件时状态是 provisional，不得写成 Outcome-supported。

当前 ADR-005 对 simulation evidence 是否能关闭 Checkpoint F 仍留有问题；建议继续将 simulation 记为 `simulation-evidence closed`，不能等同真实生产 improvement。

## 9. 隐私和数据治理

借鉴 OPA 的 decision log 脱敏、OpenTelemetry 的 structured context、SWE-agent/Inspect 的 artifact references：

- raw conversation/tool body 默认 reference-only 或加密；
- raw secrets、hidden CoT、PII 和高风险原文不进入 routing dataset；
- derived outcome 必须保留 provenance、版本、来源、删除/tombstone 关系；
- 删除原始 episode 时，派生 summary、posterior input、candidate evidence 和 holdout index 要按依赖图删除或标记不可用；
- analysis 输入采用 source/trust 标签和最小权限；
- 用户可检查、导出、删除显式反馈和 preference observation；
- 外部共享默认关闭，若未来开放必须 opt-in、redact、license、retention 和 kill switch 全部明确。

## 10. 推荐的实施顺序

### Phase A：只实现三线和确定性门控

目标：不触碰 live routing。

文件方向：

- `src/tracking/types.ts`：补 schemaVersion、event refs、source/trust、summary hash、omission provenance；
- `src/tracking/prescore.ts`：实现固定维度判定和 coverage 规则；
- `src/tracking/human-score.ts`：严格 parser 和 hard signal 优先级；
- `src/tracking/gates.ts`：只返回结构化 gate decision；
- `src/tracking/turn.ts`：异常包不读取 hidden CoT，统一经过 sanitizer；
- `src/run/supervisor.ts`：消费 assessment 并执行有限状态转换；
- `src/run/events.ts` / `src/run/event-store.ts`：追加 transition、assessment 和 evidence-link events；
- `test/unit/tracking/`、`test/integration/track/`、`test/integration/m2/`：补回放、并发、幂等和隔离测试。

### Phase B：修正 R1，建立结果向量

目标：生产仍使用 R0/R1，禁止动态 policy promotion。

- `src/routing/outcomes.ts`：增加 outcome provenance、criterion、source、weight/quality distinction；
- `src/routing/posterior.ts`：拆分 observation/prior effective sample，增加 Beta quantile 或标注近似；
- `src/routing/r1.ts`：加入 conservative fallback、cooldown/hysteresis、决策解释和 exposure refs；
- `src/evaluation/`：把 `taskSuccess`、`policyCompliance`、`userAcceptance`、cost、latency 分开；
- `test/unit/routing/`：覆盖 prior 不满足 nObsEff、version reset、tie-break、abstain、fallback。

### Phase C：离线归因和 OPE/paired harness

目标：只生成报告，不修改 active pointer。

- `src/experiments/`：sealed manifest、train/validation/holdout、隔离 replay、污染检查；
- `src/routing/`：propensity ledger、overlap/ESS、paired comparison 和预注册 OPE；
- `docs/decisions/0005-checkpoint-f-holdout-open-questions.md`：明确 primary endpoint、simulation evidence 和 real evidence 的区别；
- `docs/reports/`：生成可审计 evaluation card。

只有当联合模型能通过模拟覆盖率、校准、敏感性和跨项目/时间留出测试时，才实现 project/interaction attribution。

### Phase D：候选和晋升

目标：仍然 proposal-first。

- candidate registry 只接受一个 resource boundary；
- candidate 通过 static/replay/holdout/shadow/canary；
- 用户批准后用 CAS 更新 active pointer；
- 自动 rollback 只能回退到已知批准版本；
- approval profile、budget、cooldown、guardrail regression 版本化。

## 11. 必须新增的验收用例

### 隔离和控制

1. Execution 收到 tracking summary 引用时，仍不能把 summary 作为 authority；执行输入只能来自 TaskContext 和 supervisor 白名单 directive。
2. 同一个 assessment 重放两次只产生一个状态转换，幂等键和 CAS 生效。
3. Tracking 自由文本写“继续执行”不能改变 supervisor state。
4. Analysis 尝试写 active pointer 或 in-flight task state 被拒绝并产生 policy event。
5. summary 被截断时，mandatory omission 触发 fail-closed；三轮滚动后 privacy constraint 仍存在或明确阻塞。
6. 用户文本、工具正文和路径名中的 prompt injection 不会改变 analysis authority。

### 评分和异常

7. 同一 turn 同时出现测试失败、`7分`、`继续` 时 hard gate 唯一优先；不会重复走普通 score 路径。
8. `UNOBSERVED` 不变成 0.5；无可观察维度时 P=0；coverage 降低但不把缺失伪装成失败。
9. permission/security reject 不能被 4/5 ratio 抵消。
10. required check 没有真实 check event 时，completion claim 触发 `MISSING_REQUIRED_EVIDENCE`。
11. minor 按稳定 key 计算 2-turn/3-count，只有新确定性证据可以关闭。
12. 绿色、above-threshold turn 不读取 tool body 或 hidden CoT；建议实现为永远不注册 hidden CoT reader。

### 路由和统计

13. 无目标 cell 观测但 parent posterior 很高时，`nPriorEff` 不满足 `nObsEff≥5`。
14. `ABSTAIN/UNOBSERVED` 只记 exposure；没有调用的 shadow model 不产生 outcome。
15. 同一 interaction 观测不重复计入 model/project parent 的 live estimator。
16. 极端均值、小样本和衰减样本下，LCB 的模拟覆盖率满足预注册目标。
17. 版本改变后新 key 不继承旧 model outcome；旧数据仍可审计。
18. live policy 在任何 R0 hard constraint、high-risk whitelist 或 policy guardrail 上失败时立即回退。
19. LCB 相同和估计稀疏时，选择确定性 baseline，不因噪声抖动。
20. OPE 缺少 overlap 或 ESS 时返回 `UNOBSERVED/INVALID_ESTIMATE`，不生成 improvement claim。

### 实验和晋升

21. train/validation/holdout 之间不能共享 episode/artifact hash；holdout 被优化访问后标记 compromised。
22. replay 的缓存键包含 run ID、candidate hash、environment/evaluator version；不同预测不能错误复用旧结果。
23. paired report 的成本 CI 使用上界条件；均值通过但 CI 不通过时不能晋升。
24. promotion ledger 能重建 parent、candidate、evidence、approval、CAS expected version 和 rollback target。
25. rollback 后下一次 execution 的 active pointer 与事件日志一致。

## 14. 一句话结论

**把三线设计实现成“事件事实 → Tracking assessment → deterministic supervisor 状态转换 → 分析候选 → sealed evidence → 用户批准/CAS”的闭环；把路由复杂归因降为离线实验，把 score 与 task success 分开，把稀疏时的默认行为改成批准的保守 baseline。这样既保留原方案的安全和可回滚优点，也吸收了 Temporal、OpenTelemetry、OPA、Inspect AI、SWE-bench、MLflow、FrugalGPT、RouteLLM 和反事实评估研究中最可迁移的工程做法。

# pi-sparkle 未来开发计划

## 目标与本轮权限

**先让 Pi 更顺利地交付真实改动，再用真实结果决定 Sparkle 要增加什么。** 不以 PR 数、测试数或新模块数衡量进展。

本轮用户要求：尝试整合现有 PR，有用的增加，没用的删除，并给出清楚的整体架构和未来计划。这允许处理本轮相关旧 PR/分支，不授权修改原 Soul、调用付费任务、发布 npm、解除无关学习/调度冻结或批量删除私有证据。

下列阶段是建议路线，不是批准所有后续实现。当前具体任务与候选状态只维护在 [tasks/plan.md](../tasks/plan.md)；架构见 [framework.md](framework.md)。既有 ADR 的优先级、比较目标、安全与授权边界继续有效。下文采用“阶段 A–E”，不复用旧 M0–M7，以免把历史方案误认为当前施工单。

## 阶段 A：收口已有能力，不再囤积 PR

**交付：一个能准备、执行、检查并明确应用/丢弃任务的整合主干。当前唯一实施主线。**

- 合并 #132 离线 Node 准备与 #103 容量一致性的有用部分，追通 preflight → worker → hold → apply，复用仍适用的验证；新整合点做定向验证。
- #68 的 host/routing、#102 的审批委派先看当前入口是否真正需要。必要能力提取到当前核心；重复、失效或不服务当前结果的提案关闭并删除无用分支，保留 Git/PR 历史可追溯性，不整包恢复冻结模块。
- 清理活动计划中的过期待办、重复状态和陈旧等待条件；旧失败、未知费用及未解决安全义务保留一次引用，不通过删除文档把问题“完成”。

**完成判定：** 整合候选的受影响验证和必要独立审查通过；主干 CI 成功；废弃 PR 有明确去留原因；执行版本是否更新单独记录，不把 merge 当作运行环境已更新。

**负责人：** 实现者负责代码与受影响验证；独立审查者只追用户可见链和发布阻塞；协调者负责取舍、整合、清理和状态。

**不做：** 新模型路由、自动晋升、通用队列/持久化重写。方法两次失败则缩成最小阻塞修复，不为清空 PR 列表牺牲兼容或安全。

## 阶段 B：让五个不同真实任务真正跑完

**交付：五个不同任务的可核对结果，不是五次重复试跑或新的配置演示。**

依赖阶段 A、实际执行 runtime 更新、新账本流程和既有任务准入；付费任务仍按单独有效授权执行。本轮不运行付费试验。

- 新账本从第 44 次尝试开始；历史 43 次汇总独立保留，缺失记录不猜补，unknown 不改零。
- 优先验证 H2：依赖、工具链、TaskSpec 输入和准备流程的问题是否在后续不同任务中减少。
- 每个任务记录：最终独立检查、是否交付/应用、人工介入与返工、准备/执行/评审耗时、全部尝试成本与覆盖缺口、失败原因及实际效果状态。
- 继续使用自身真实 backlog 与隔离 Soul 需求；原 Soul 应用必须单独明确授权。需要比较时匹配模型、预算、环境和输入，不把人工补救算成原始自动成功。

**完成判定：** 所有尝试都记录；五个不同任务形成结果窗口；能分清“环境没准备好、worker 超时、供应商问题、代码缺陷”，并知道下一类最值得解决的问题。

**停止规则：** 不因单次失败开一个永久机制。重复根因达到两次或成本显著时归为一类处理；原因未知先保存事实，换一次有界诊断，不反复原样重跑。

## 阶段 C：只修影响真实交付最多的一类问题

**交付：下一个真实任务更少人工介入，而不是更多约束或更多设置页。**

优先顺序来自 ADR-011 和真实窗口：先准备/环境/输入（H2），再预声明时间预算（H1）与供应商原因。后续观测若要求改变已确认优先级，由用户决定，不自行换序。

| 原因 | 最小产品动作 | 验收 |
|---|---|---|
| 准备/输入 | 改共享 TaskSpec 模板、依赖准备和基础检查；给可行动的环境错误 | 后续不同任务不再在相同准备点失败 |
| 时间不足 | 明确总时间与准备/worker/check 分配；在动作边界报告剩余资源 | 不重置累计限额；取消后真实结算或保留未结 |
| 供应商超时/用量缺失 | 清楚归因并维持当前重试/费用边界 | 不叠加重试、不隐式换更贵模型、不把无 usage 算零 |
| 模型代码缺陷 | 改上下文选择、可见检查和有限修复反馈 | 独立检查拒绝错误候选，后续任务更少人工救场 |

只新增有真实失败支撑的通用修复。可选 limits/配方不自动变成要求每个用户填写的新表单。批准后的模板、检查或上下文改进仍通过现有资源机制，不另建一套“学习系统”。

## 阶段 D：做成别人能安装和使用的开发者预览

**交付：仓库外用户可以按短文档完成一个任务，知道当前支持范围和失败后的处理方法。**

- 选定并收窄一个主入口，CLI 与 Pi 扩展复用任务核心，减少必须理解的内部概念；保留现有必要兼容路径。
- 验证真实 Pi 宿主所需的 prompt、模型/thinking、工具和批准资源传递；逐项记录等价与缺口，不宣称自动继承所有 skills/MCP。
- 先确认外部消费者真正需要哪些 API，再稳定窄 SDK/export 与包内示例。旧模块只有在调用、打包和兼容测试确认无用后删除，不先做全库大迁移。
- 选择有实际环境支持的语言案例，验证安装后 preflight → execute → independent check → explicit apply/discard。各平台分别记证据。

**完成判定：** 仓库外消费者能运行；支持矩阵清楚；隐私/隔离/取消/费用/效果未结等既有发布义务完成；版本、安装、升级和回退路径明确。正式发布及重要评测另需授权，不因 CI 绿自动发包。

跨进程写恢复 B1/B2 只在真实任务显示中断需求时进入，不为阶段编号主动扩大范围。保留候选后重新核验仍优于从 JSON 伪造旧权限。

## 阶段 E：证明收益，再有限自动化

**交付：能回答“为什么不直接用 Pi”，之后才考虑自动采用某一类优化。**

- 有足够真实改进信号后再开展预声明比较；旧 15 任务义务、ADR-010 的 30 任务公共比较和新的真实任务窗口分别保留，不互相充数。
- 比较 direct Pi、Sparkle core 与轻量验证对照；模型/环境/预算/信息匹配，按逻辑任务分组统计，失败、拒绝、重试、人工审查全部计入成本和时间。
- 目标保持：正确交付非劣界 -3 个百分点；有充分依据的缺陷相对减少至少 50%；每次正确交付成本不超过 direct Pi 的 1.3 倍。费用缺失或分母不足时明确“证据不足”。
- 某类经批准提案在后续真实任务中证明有效、监测/停止/回滚链验证且范围另获授权后，才考虑该类型有限自动化；不推广到权限、凭据、安全设置或全局自动晋升。

**不达标怎么办：** 保留确有价值的候选隔离、检查和审计工具，不继续包装为自优化平台；先缩产品再加机制。研究成本不能靠“未来会有效”抵扣。

## 本轮不启动的方向

通用多 Agent 框架、另一套调度/持久系统、全量向量记忆、全语言/全平台兼容、自动供应商路由、自动资源晋升、P4/P5、无人值守付费 benchmark。现有未解决安全义务不因延期这些方向而消失。

## 每次交付只回答五件事

1. 用户新增能做什么；2. 是否已经合入；3. 哪个实际运行环境可用；4. 下一步唯一结果与真正阻塞；5. 哪些费用、效果和收益仍未知。

没有用户可见增量时，测试数和审查轮数不当作产品进度。阶段验收足够就进入下一结果，不继续叠防御性边界补丁。

# pi-sparkle 未来开发计划

## 目标与权限

**北极星：** 在 Pi 里说一句需求，系统把它做成一个检查过、可以放心应用的改动；较大的目标能持续推进，只在需要你做决定时才打扰你。

**衡量标准：** 与直接使用 Pi 相比，正确交付更多、人工介入更少、每次正确交付的总耗时和总费用更低。总耗时里先看人的那部分：每次正确交付消耗的人工和协调者时间，包括写任务、评审、介入和等待决定。agent 系统的瓶颈通常在验证和审阅，不在生成。PR 数、测试数和新模块数都不算进展。

**结构依据：** [ADR-012](decisions/0012-three-pillar-architecture.md) 规定了以下内容：

- 产品分三个板块：单任务、长任务、模型分配与 Worker 池；
- 板块之间共用底座和自进化反馈环；
- 每个板块的成熟度分为 L0–L3；
- 当前解冻的范围。

架构说明见 [framework.md](framework.md)。当前任务与候选状态只维护在 [tasks/plan.md](../tasks/plan.md)。ADR-010/011 的安全、预算、比较目标和授权边界继续有效。

**编号约定：** 时间进度用“阶段 A–E”，成熟度用 L0–L3。旧 M0–M7、Phase、R 编号只作历史追溯。

**外部对照（DevFest 2026 杭州站，2026-10-31）：** 几场分享（多 Agent 生产化、Physical AI、RSI 自我改进、Antigravity）都把“从 Demo 到生产”落在评测、门禁、失败数据和成本可见性上，与本项目方向一致。下表只用于排序参考：讲者的说法未经核实，不作为证据，也不解冻任何冻结项。

**外部对照（OpenAI《Building an AI-Native Engineering Team》，2026-11-06 阅读）：** 文章按“委派—审阅—拍板”描述 agent 在开发各阶段的分工，强调先确认 agent 的命令和检查跑得通、测试与实现分开、评审要准而不在多。它是厂商指南，除引用的 METR 数据外没有可核实的数字，同样只用于排序参考；表中标“（OpenAI）”的行来自这篇文章。对照本项目的数据，挡路的主要不是模型：新账本第 44–46 次的三次非正确交付，两次是供应商 502，一次是应用被拒；历史 31 次非正确交付按 owner 的解释性分组，准备/环境/输入 13 次、worker 超时 6 次、供应商 6 次，模型代码缺陷只有 4 次。

## 阶段 A：收口

**交付：一个真实 Node 任务能完整走完准备 → 执行 → 检查 → 应用，新版本已安装到实际执行环境。**

- 已完成：#140 合并，准备好的 Node 依赖产物可以一路保留到应用；执行环境已更新到包含它的主干；#138 已关闭。
- 第 46 次已通过两项宿主检查，走到应用时被拒：pi-sparkle 的 `.gitattributes` 设了 `text`/`eol`，精确应用的属性规则一律拒绝（I-18）。按 owner 2026-11-06 认同的方向 (a)，#156（2026-11-10 合并）允许可以证明不改变字节的 `text`/`eol` 设置。Soul 有 `eol=crlf` 文件，会改变字节，不在 (a) 之内，另行决定。
- #156 还把这次失败推广为按类修复：预检复用应用自己的只读前置判定（源仓库干净并处在候选版本、Git 属性、源快照与 Git 树一致、文件数和体积上限），应用必然被拒的源仓库在调用模型前就按具体原因拒绝，应用时照样重查。重新验证之前的应用拒绝原因由宿主生成并显示在 CLI 中，检查器的原始输出仍只留在私有证据里；重新验证开始后的原因和尝试记录中的原因还没做。合并时的证据和两处不足（没有退出码为 0 的本地 gate；跨家族评审来自 Gemini，不是 Codex）记在 I-18。
- 此前的测试只验证带 `text`/`eol` 属性时应用会拒绝，没有覆盖真实项目的常见设置。#156 的测试从 pi-sparkle 自己的形态开始：整个仓库 `* text=auto eol=lf`、`text` 未设置的二进制文件，再加上工作区含 CRLF 字节的仓库（仍应拒绝）；其他出过问题的仓库形态先确认已有回归测试，缺的再补。
- #144（rebase 后的 #103，整候选容量 4096 文件 / 32 MiB）只在完整 pi-sparkle 检出上做任务时需要，不挡第 47 次。启用离线 Node 准备时，交付文件和依赖产物要共用 1024 个文件 / 16 MiB 的预算，而 pi-sparkle 自己的 node_modules 约有 1.8 万个文件，这种情况另需一次决定。
- Git 低于 2.36 时（不支持 `worktree list -z`），在调用模型前拒绝，并给出升级提示；doctor 中显示同一项检查。
- 第 47 次（2026-11-10，执行环境 `c3647f19`）在新副本上复用第 44 次的 TaskSpec，完整走到应用：零模型预检通过，一次模型调用，两项宿主检查通过，应用前重新验证后提交到副本；应用后任务的两项检查在副本里通过。已知费用约 US$0.04，过程中 0 次介入。移植 PR #157 的 CI 是原项目检查，#157 需 owner 合并。

**完成判定：**

- 一次尝试走到应用并成功，已记入私有账本；
- 执行环境的版本单独记录；
- 安全核心改动的 Windows 串行本地 gate 结果单独记录。

## 阶段 B：度量（单任务 L1 的记录部分）

**交付：每次尝试的结果都看得清，并知道最常见的失败是什么。**

- 复用 `scripts/real-task-record.mjs` 与 `real-task-summary.mjs`，不另建存储。
- 每次尝试记录以下内容：
  - 最终独立检查结果；
  - 是否交付和应用；
  - 人工介入与返工；
  - 准备、执行、检查、评审各阶段的耗时；
  - 写任务的时长（每个新任务都记，复用已有 TaskSpec 记 0）；
  - 全部费用及未覆盖的部分；
  - 失败类别；
  - 返工次数（检查失败后再次执行的轮数，未观察到的记 unknown）；
  - 能拿到时，按阶段拆分的 token 用量（拿不到的记 unknown，不估算）。
- 第 47–49 次和之后经 owner 授权的尝试：凑齐 5 个不同的真实任务，用现有队列管理。第 44–46 次是同一个任务。
- **选题规则：**
  - 来源：现有 6 个候选任务（第 44 次的任务和私有队列 q01–q05）里有 5 个改项目自己的开发脚本。第 47–49 次优先改产品代码的任务；第 49 次以后加入隔离 Soul 副本上的任务，这需要先定依赖预算，Soul 的 `eol=crlf` 文件也在 I-18 方向 (a) 之外。
  - 难度：除了打通管道用的小任务，要有多文件、跨模块、边界情况多的任务。现有候选的预期改动都在 1–15 行；历史 43 次没有观察到逃逸缺陷，而按 ADR-010，direct Pi 缺陷为零时无法证明缺陷相对减少。
  - 移植成本：队列条目写明改动移植回原项目要走哪条路（普通 PR、接近安全核心、冻结 CLI 审阅），其他条件相同时先做移植便宜的。
- **人工时间：** 汇总给出每次正确交付消耗的人工和协调者时间（写任务、评审、介入；等待决定的时间写进 notes），只用现有字段，缺的记 unknown。新账本前三次已记录的评审耗时约 294 秒，是准备、模型、检查三段机器耗时之和（约 98 秒）的 3 倍，还不算第 44 次记录注明的约 3 小时无人察觉的等待。样本小，只作信号。
- 新账本从第 44 次开始。历史 43 次的汇总单独保留；缺失的数据不猜补，unknown 不改记为零。

**完成判定：**

- 5 个任务的记录齐全，其中至少 4 个费用已知；
- 能分清以下几类失败原因：环境没准备好、输入问题、超时、供应商问题、代码缺陷；
- 能算出每次正确交付的人工和协调者时间，缺的记 unknown；
- 选出下一类最值得解决的问题。

**汇总要求（复用 `real-task-summary.mjs`，不新建存储）：** 输出非正确交付的失败类别排序，按次数从多到少排；次数相同时按已知费用排。每一类同时列出已知费用、费用未知的次数和人工介入次数，没有分类的尝试单列为“未分类”。只排序、不打分：费用未知时不计算“次数 × 费用”。这一项是 R2“按频次 × 成本选类”的工具化，改动脚本时需先写失败测试，并走普通 PR 流程。

## 阶段 C：单任务可靠，并提供 Pi 内无命令入口

**交付：在 Pi 里直接说需求就能完成任务，最多确认两次；最常见的那类失败变少。**

| 切片 | 内容 | 对应等级 |
|---|---|---|
| C1 | 针对阶段 B 选出的失败类别做通用修复，优先改共享输入：模板、准备配方、上下文规则、检查配方。修复方案以提案形式提出，批准后生效 | 单任务 L2 |
| C2 | 起草工具：Pi 只提出目标和可改范围；检查和限额由宿主生成；确认后执行 | 单任务 L1 |
| C3 | 用确认对话框代替 apply/discard 命令，增加状态显示；原命令保留，保证兼容 | 单任务 L1 |
| C4 | 无界面模式默认拒绝应用，按宿主策略放行 | 底座 |
| C5 | 宿主按角色设定模型档位；只在指定的失败类别下升级；模型不能自己选择 | 3a L1 |
| C6 | 异家族只读审查作为可选的检查前步骤，只提供参考意见 | 3b L1 |
| C8 | 交付说明：每次交付自动生成一页说明（改了什么、为什么、证据在哪、哪些没有验证），内容只取自已有的投影和检查记录，不新增证据格式 | 单任务 L1 |
| C7 | 第 50–54 次尝试，与阶段 B 对比 | 验证 |

只新增有真实失败支撑的通用修复。可选配方不能变成每个用户都必须填写的新表单。C2 和 C8 的先后按阶段 B 的人工时间构成决定：写任务耗时多就先做 C2，评审耗时多就先做 C8。

**C6 审查的使用规则：** 异家族审查相当于一个 LLM 软裁判，只能加严，不能放行。硬检查失败时，结论不受审查意见影响。审查意见计入任何判定之前，先在不少于 20 条人工标注过的历史交付上测一致率，并记录结果；一致率不达标时，只作参考展示。标注方法先用现有的 PR 评审记录试点：每条意见标为导致修改、被有据反驳或延后，算出精度。审查篇幅按风险控制，低风险改动只报阻塞问题。

**完成判定：**

- 在 C7 中，目标失败类别比阶段 B 少；
- 在 Pi 里完成一个任务不需要输入命令。

**审阅要求：** 新增的工具或命令接口、TaskSpec 字段，以及冻结的 CLI/事件/JSON 接口变更，合并前都要经所有者审阅。

## 阶段 D：长任务 L1，并让外部用户可用

**交付：多步目标可以交给系统持续推进；仓库外的用户能安装和使用。**

- 目标文件归你所有。目标拆成里程碑，里程碑拆成工作项，复用 work-item-store。协调者只负责选下一项、分派和汇报，不配置写工具。
- 完整检查和 CI 改为异步执行，结果作为事件回到会话。异步执行仍计入预算，也可以取消。
- 链式召回：记录带摘要和关联 ID，需要时再逐层展开。续接时重新核验，不从 JSON 恢复权限。
- Watchdog 定时检查：有没有用户可见的进展、是否偏离目标、同类问题是否反复出现。它只能暂停和提醒，不能修改规则。
- 熔断：同一工作项连续两次以同一失败类别结束时，自动暂停该工作项并提醒你，不再自动重试；恢复需要你确认或输入发生了变化。
- 用 fake executor 零费用测试三种情况：被阻塞、中断、反复失败。
- PR 闭环（L2 起步）：
  - 工作项订阅自己的 PR，CI 结果和评审意见直接送到对应工作项；
  - Agent 不合并自己的 PR；
  - 批准必须覆盖当前 head。
- 外部可用：
  - 确定一个主入口；
  - 提供安装文档、支持矩阵和回退方法；
  - 隐私、隔离等既有发布义务必须完成。

**完成判定：**

- 在自身 backlog 上完成一个至少 3 个工作项的目标；
- 期间至少中断一次并成功续接；
- 统计人工介入次数；
- fake 测试的三种情况都能正确识别。

跨进程写恢复 B1/B2 只在真实任务确实需要中断恢复时才做。

## 阶段 E：并行、路由建议、受控自动化，并证明收益

- **3b L2：** 独立的工作项可以并行，条件是：候选互相独立、写入范围不重叠、逐个检查后串行应用。前提是长任务达到 L1。
- **3a L2：** 基于记录给出 shadow 推荐，并与实际结果对比。
- **自动采用：** 已证明有效的提案类型进入 auto（ADR-011 第 2 步）。前提是有证据，并获得所有者另行授权。
  - 放量方式：先只用于约 10% 的符合条件任务，观察窗口内指标不退化再扩大；任何一项退化即回滚。
  - 被拒绝或回滚的提案和它的评测结果都保留在现有 registry 中，不删除。
- **扩充开发集：** 可以从真实失败任务合成变体题，扩充开发和回归用的题目，但合成题不进入 holdout，也不计入收益比较。
- **收益比较：** 按 ADR-010，对比 direct Pi、Sparkle core 和轻量验证三组，并预先声明比较方案：
  - 正确交付率的非劣界为 -3 个百分点；
  - 缺陷相对减少至少 50%；
  - 每次正确交付的成本不超过 direct Pi 的 1.3 倍。

  缺少费用数据、或样本数量不足时，结论写“证据不足”。题目要包含 direct Pi 可能出错的任务（多文件、跨模块、边界情况多），否则 direct Pi 缺陷为零，缺陷减少无从证明。付费评测和发布需要另行授权。

**不达标怎么办：** 保留确有价值的部分，即候选隔离、检查和审计；先缩小产品范围，不再加机制。

## 仍冻结

以下方向不推进：

- 学习型或自动路由（F-PROD 关闭前）
- 自动晋升
- 动态团队和通用多 Agent 框架
- 云端常驻、端侧 daemon、IM 监听
- 全量向量记忆
- 无人值守的付费 benchmark
- P4/P5

现有尚未解决的安全义务不会因为这些方向延期而消失。

## 每次交付只回答五件事

1. 用户新增了什么能力；
2. 是否已经合入；
3. 哪个实际运行环境可以用；
4. 下一步唯一要交付的结果，以及真正的阻塞；
5. 哪些费用、效果和收益仍然未知。

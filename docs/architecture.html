Pi-sparkle / Architecture

简单任务直接做，
复杂任务按需深入。

一个以 Pi 为执行基础的开发框架。它把目标变成可检查的改动，也让经验、插件和项目协作逐步接入。

从一个场景开始 →

轻核心 · 明确职责 · 持续校正

用户交来一项工作

“修复登录失败。
如果发现相关的大问题，
一起处理好。”
先推进读取相关代码，完成改动
再深入出现证据，再增加分析与协作

这里解释的是已接受的当前设计。已有基础与待接线能力会分别标注。设计被接受，不代表迁移、生产验证或收益评测已经完成。

讲解提示

先让听众想象一项日常修复。框架应帮助任务开始，而不要求每个小问题先经过完整项目管理流程。后面所有模块都围绕这个场景解释。

主讲可按章节走，也可直接点击节点。每一次推进由讲解者控制，没有自动播放。

02 / Purpose

Pi 执行，Sparkle 组织工作。

保留成熟执行基础，把框架的精力放在任务边界、可靠交付和可复用能力上。

执行基础

Pi 负责
模型与工具的循环。

  • 模型调用与工具交互复用执行能力，通过适配层连接项目。
  • 生命周期接入事件、停止、取消与结算需要按实际接口验证。

框架职责

Sparkle 负责
把一项工作完成。

  • 目标、范围与下一步选择直接任务或项目队列，按证据调整计划。
  • 改动、检查与恢复跟踪真实发生的效果，不把模型自述当作验收。
  • 按需扩展插件、偏好、项目推进和离线学习共用执行与事实层。

架构形式：先保持一个部署单元，默认一个执行者。四个核心是责任归属，不是四个服务，也不意味着每项任务多出四轮模型调用。

讲解提示

回答“为什么不直接用 Pi”：Sparkle 增加的是围绕任务和项目的组织能力。回答“为什么不自己造引擎”：模型与工具循环已有基础，框架应保留清晰的适配边界。

03 / Responsibilities

四个职责，共同围绕一项任务。

先弄清“谁负责什么”，再看目录与接口。这里没有强制流水线。

点击一个职责，查看它的决定、输入与边界。

任务与授权

决定做什么，以及下一步做什么。

接收目标、已有授权与当前事实，选择轻任务或已有项目队列。观察者可以提出发现，控制者保留行动决定权。

复用 DevelopmentController、NativeWriteSession 与现有入口。任务视图来自既有事实，不再造第三份 Task 状态。

执行与资源

让 Pi 与工具执行，并知道何时真的停下。

负责适配、工具生命周期、用量观测和取消。供应商重试在一处处理，避免每层都重试而放大开销。

保留现有运行路径，先统一必要端口。取消请求与实际停止是不同事件，未结束的效果需要对账。

工作区与检查

把代码改动与实际验证对象绑定。

提供相关上下文、搜索、范围读取、精确修改与命名诊断。检查深度与影响匹配，既有严格验收不降级。

缓存可以复用准备工作，不能替代对当前候选的最终检查，也不能自行产生 apply 权限。

状态与恢复

记录发生过的事实，恢复时先查清效果。

队列、运行记录、ActionLedger 与 Git 各自保有既有权威。项目进展只是这些事实的组合，不另存一套“完成状态”。

未知外部效果保持未决。重启不盲目重复写入，旧检查也不能自动证明新基线有效。

已有基础：执行器、候选工作区、队列和事实记录已经存在。待整理：统一薄入口、公开窄接口与清晰依赖方向。

对应代码在哪里？

src/development/controller.ts、src/native/write-session.ts 管任务，src/pi-adapter/pi-executor.ts 接执行，src/execution/independent-check.ts 与 src/context/index.ts 管相关检查和上下文，src/development/work-item-store.ts 与运行记录承载事实。完整映射见 当前架构文档。

04 / A task

修登录 Bug，从相关代码开始。

任务清楚时直接推进。需要更多能力时，沿用已有工作继续深入。

  1. 01读取相关代码
  2. 02修改候选
  3. 03解释失败
  4. 04修复关联问题
  5. 05检查与交付

先找到登录路径和已有测试

当前要求与范围优先，按需读取相关信息。

从错误位置、授权路径、符号及导入邻域寻找证据。没有可用代码地图时，回退到搜索与范围读取。普通任务无需先建立全仓索引。

上下文装不下时压缩历史或明确返回容量问题，不能悄悄删掉本次目标与验收要求。

一个执行者完成局部修改

复用已有候选与授权，不先搭建完整任务图。

明确、局部、可逆的任务走直接路径。保留必要的范围约束、取消能力与真实改动记录，不要求逐任务填写金额表单。

一次编译失败，先做局部修复

先判断原因，再决定是否增加流程。

可定位的语法或类型错误由当前执行者修正。工具超时、供应商限流与代码缺陷分开处理，不因一个环境故障立即换更贵模型。

测试暴露共享鉴权缺陷

相关的大问题可以及时修，观察者不抢写。

记录当前快照与证据，必要时只读分析依赖。已有授权内的可逆修复直接进行。需要更大改动时先准备独立修复流，已有授权涵盖便继续，不重复确认。

交付的是检查过的当前改动

基线变了，原候选就要重建或重新验证。

运行与改动相关的检查，保留严格 develop 路径的原有验收语义。说明实际完成、用量已知部分与尚未验证的范围。

没有全量验证就不声称全量通过，候选已接受也不自动代表已应用到源码。

讲解提示

这条路径不要求五个独立 agent。默认仍是一个执行者，步骤表示任务进展。深层缺陷的出现才触发附加分析，已经取得的上下文和证据继续使用。

05 / Adaptation

边做边观察，按证据改变下一步。

持续观察主要消费已有事件。只有值得解释的新问题，才启动短时只读分析。

  1. 01筛选与去重
  2. 02按影响分流
  3. 03安全地修复
  4. 04接续原目标

事件先经过便宜的规则

相同原因、同一快照的日志，合并成一条发现。

工具结果、测试与源码变化可以触发观察。普通成功读取、文本流更新和重复日志不必调用模型。语义分析只读稳定快照，返回时先确认版本仍有效。

分析队列可以压缩过期摘要，但取消、计费、claim 与外部效果等原始事实不能丢弃。派生分析采用有限并发，避免不断重规划。

严重程度与证据强度分别判断

已证实的危险立即停止受影响动作，保存事实并对账。
范围内的缺陷到合适的动作边界，交给当前执行者修复。
超范围的阻塞准备关联修复方案，复用既有授权；只补缺少的授权。
无关的建议记入待办，不打断当前目标。

先确保旧动作真的结束

发出取消，等待真实停止并对账，然后移交写入权。

观察者只报告证据，不直接修改候选。当前执行者继续修，或在写入所有权明确后建立独立修复任务。不能只释放 claim 就启动另一个写者。

进程树清理仍是实施优先项。外层命令退出，不能证明嵌套子进程已停止写文件。

计划可变，已发生的事实保留

更新当前输入和下一步，重新核对受影响基线。

用户新指令、当前偏好与任务事实可以更新。运行中的 Pi / 插件代码、验收契约和授权边界保持稳定绑定；观察器不能把诊断伪装成用户授权。

首期使用现有 block / release 和独立修复会话。未来的计划修订只针对待执行项，不原地重写运行中或已完成的定义。

已有：工具、检查与运行事件。待接线：发现分流、版本化分析与修复接续。动态发现的策略原型不等于真实进程和生产并发已通过验证。

06 / Proportion

流程的重量，跟着任务变化。

复杂度决定规划与协作，风险决定检查与授权。预算继承已有设置，不要求每个小任务重新填写。

  1. 路径 A局部明确任务
  2. 路径 B普通多模块任务
  3. 路径 C复杂长线任务

直接执行，加相关检查

省去独立规划者、项目队列与无关全量研究。

位置、目标与影响都清楚时，从实际工作开始。文件少不等于风险低：一个数据迁移或公共接口修改，仍需要相应检查。

短计划，加一个执行者

明确接口与验收，保留已有候选持续推进。

遇到新依赖或契约影响时升级。一次可定位错误通常在当前路径修复；同样的失败没有新证据时，才换诊断路径或集中调查。

需要时启用队列与选择性并行

只把适合拆分的工作分出去。

依赖、共享写范围和验收决定任务边界。复杂的只读研究可以并行，多个写者不能争用同一候选。阶段结束前避免反复升降流程。

默认观察记录已知用量、未知价格与覆盖率。普通模式不因未知价格停止。
按需提醒继承项目或会话阈值，触发提醒。已有明确上限不能被静默撤销。
可选严格准入仅对有可靠费用上界的配置预留。不是跨供应商最终账单保证。
模型路由如何控制成本？

先尊重用户指定并筛选工具、上下文、供应商等能力，再在已测可用配置中选择合适成本档。先区分环境、工具、provider 与功能失败，只有功能不足或高不确定性才考虑升级模型。没有校准数据时使用配置主模型。

费用包括失败、取消、重试和辅助分析；未知部分不记为零。当前 CostGate 是回合后的观测停机，严格调用前预留与跨层结算仍需实现和验证。

怎样防止框架过饱和？

默认一个执行者，未触发插件不执行入口，研究和晋升模块离开默认运行路径，每类状态只有一个权威。观察额外模型调用、启动依赖、首次有效编辑时间、返工和费用覆盖率。没有净收益证据的新能力不进入默认路径。

07 / Compatibility

跟进 Pi，以兼容行为作为入口。

产品不永久绑定一个内核版本。每项运行仍记录自己的精确组合，保持恢复和问题复现的依据。

  1. 01发现候选
  2. 02隔离验证
  3. 03新任务采用
  4. 04旧运行保留

候选发现离开任务关键路径

先用已安装、已合格的组合接任务。

管理命令或后台检查发现候选。选择自动稳定通道后，兼容更新可按该策略采用，无需每个小版本再次确认；离线与精确版本模式保留。

验证行为，不只检查方法名称

独立安装、独立进程，检查事件、工具、取消与停止时序。

例如停止钩子即使只是改名，调用时间变化也可能让费用更新晚于下一次请求。资格测试必须覆盖“观察本轮用量后，在下一次 provider 调用前停止”。

破坏性变更需要更新适配器，完成后仍走同一认证流程。任何未来版本零适配不在承诺内。

一个新运行绑定一组已验证组合

候选合格后发布资格记录，再更新采用指针。

新 root run 选择 runtime generation，子任务和重试继承。首期优先一个 root run 一个受管进程，不先建设常驻多版本池。

内嵌执行器与宿主 Pi 扩展是两个兼容边界。宿主本体更新需要新进程，扩展 reload 不能证明已加载内核完成更新。

在途任务继续原组合，恢复也有原绑定

候选失败保留已知可用版本，已有外部效果不盲目重放。

运行引用和恢复需要共同阻止旧组合被过早回收。共享状态格式迁移先保留副本并确保旧写者停止，回退代码不等于自动兼容新数据。

身份遵循 ADR-008：不透明版本化标识与必要的精确字节比较，不新增第一方加密哈希或防篡改保证。

当前任务继续绑定原执行组合，计划和当前输入仍可调整。
/
后续任务选择通过验证的新组合，失败时继续使用已知可用版本。

已有：Pi 适配层与部分契约检查。待实现：真实候选矩阵、受管 generation 与恢复引用。升级宿主 Pi CLI 不会自动更新内嵌 core。

08 / Preferences & learning

先理解这次需要什么，再积累长期经验。

少量可纠正偏好，加上当前目标、阶段与阻塞，通常比一份大而全人格档案更有用。

长期默认“平时回答简短。”
这次的明确要求“详细解释，方便宣讲。”
  1. 即时需求本次详细
  2. 可解释记忆来源与范围
  3. 长期改进先证据后试用

本次详细，长期默认保持原样

当前明确要求优先，任务结束不自动改写永久偏好。

先过滤用户身份、项目、时效和相关性，再解决冲突。明确纠正本身就是显式要求；“以后中文”直接更新长期偏好，“本次详细”直接更新任务覆盖层，均无需策略晋升。

能查看、能纠正，也能删除

偏好记录为什么生效、用于哪里、何时过期。

跨项目不混用约定，弱推断不能覆盖显式表达。删除使派生缓存失效，并阻止旧来源把同一事实重新记回来。没有相关证据时使用默认，不编造用户画像。

偏好影响表达和协作方式，不产生部署、花费或写入授权，也不允许隐藏真实失败。

推断策略走受控学习闭环

记录事实，分清原因，离线比较，再有限试用。

代码错误、provider 故障、需求变化和表达不合适分开归因。正确性与实际验收是门槛，再比较返工、费用、延迟及用户纠正。满意度只是一项反馈。

第一阶段沿用现有批准与回滚流程。之后可在一次性启用的有限范围自动试用低风险策略，前提是监测、停止和回滚真正可用。

已有：preferences 的显式/推断区分、纠正、删除与墓碑记录，auto-loop 的收集和提案。待接线：当前任务覆盖、逐项时效来源，以及受控在线试用和自动回滚。

长期自优化能不能修改框架自身？

可以把改进建议转成普通开发任务，产生可检查候选，并复用已有授权、检查与应用流程。低风险策略自动试用不包括偷偷替换运行中的内核、改动权限或检查器。模型推断的策略和用户明确设置是不同路径。

09 / Extensions

插件作者，从一个小贡献开始。

首批稳定目标只有上下文与诊断。公开接口保持窄小，理解内部所有目录不是开发插件的前提。

  1. 插件作者sdk
  2. 嵌入开发者host
  3. 验证贡献testing

一个 manifest，一种贡献，一个 fixture

context 补相关信息，diagnostic 提供可解释检查。

先读取声明并匹配需要，首次请求时再加载。并发激活共享一次加载，验证后一次发布，失败不留下半注册状态。

示例设计：Python 项目需要时激活语言插件，提供符号上下文与命名诊断。必要诊断不可用时明确报 unavailable，不能伪造通过。

宿主掌握编排与应用权威

CLI、Pi 扩展与嵌入应用复用任务入口。

宿主负责 start / resume / inspect 及既有授权下的 review / apply。插件不直接获得凭据、原始存储或验收应用能力。通用 tool / observer 先保留实验契约。

可信同进程插件不具备安全沙箱隔离。真正需要执行不可信插件时，必须另行设计进程与权限边界。

在仓库外验证公开契约

打包、安装、编译、运行最小消费者。

fixture 检查贡献的输入输出、取消、失效和失败语义。禁用插件后基础任务仍能运行。收窄旧深导入要分步迁移，避免突然截断现有消费者。

测试工具只能证明约定行为，不能把测试结果升级为生产验收权限。

设计目标，尚未生产公开：pi-sparkle/sdk、pi-sparkle/host 与 pi-sparkle/testing 是计划中的稳定入口。不要把这里的名称当作已经可安装的公共 API。

能力激活时发生什么？

声明匹配 → API 与宿主能力核对 → 按需加载 → 暂存注册 → 唯一标识检查 → 一次发布。可选上下文失败可回退基础检索，必要诊断失败则保留不可用状态。卸载后过期提案不得改变新任务；迟到的效果收据与用量仍由宿主记录、对账。

完整输入、输出、退路与验证指标见 算法说明。

10 / Projects

项目推进，继续使用同一套事实。

在已有队列上增加薄协调函数。目标、依赖和恢复可以跨天延续，任务的完成状态仍只有一个权威。

  1. 01先对账
  2. 02选择可执行项
  3. 03复用执行器
  4. 04记录并继续

恢复时先查未决效果

读取队列、当前源码和收据，不盲目重放写操作。

上次的结果、失败经验与决策形成按需检索视图。源码变化和未知效果只阻塞受影响项，无关本地工作可以继续。

沿用现有依赖选择与锁内认领

并发的继续请求，也只能认领一次。

依赖需要真正进入当前源。候选已接受但尚未集成，不能据此解锁后续任务。新增目标先成为草稿，接纳后才进入可执行队列。

advanceProject 只负责协调

调用已有 controller，不再建第三套调度器。

普通单任务不必经过项目队列。长线模式才按需要使用依赖、有限批次和恢复；关闭协调函数仍可手动运行下一项。

结果回到既有事实层

项目进展是投影，外部系统不是隐含执行命令。

连接器先把 issue 只读导入草稿，再考虑写自己的进展区。重复事件去重，丢响应先查询对账，远端人工编辑发生冲突时不覆盖。

GitHub 的通用写接口不能凭 ETag 获得原子比较写入保证。后台调度、自动合并与双向同步仍是后续能力。

已有：WorkQueue、项目快照、有限串行 batch 与候选检查。待实现：薄项目推进、按需决策检索和连接器。有限 batch 不等于常驻项目经理。

取消后，不再有残留写入

验收重点：观察真实文件写入停止，确认未决效果和迟到事件；不能只断言 abort 信号已经发出。

轻任务入口与窄 SDK

补小工具，明确四个 owner，分步收窄依赖。

搜索、范围读取、精确修改与命名诊断先改善日常体验。复用 NativeWriteSession 建直接入口，不强制队列和额外规划调用。SDK 用仓库外消费者验证。

目录整理、持久化格式与算法效果变更分开提交。禁止为一次大搬家同时更换所有边界。

先展示发现，再逐步开放范围内修复。

绑定证据版本，真实停止后才移交写入。接入已知费用、未知部分与覆盖率；采用规则路由和显式任务覆盖层。严格准入预留作为单独的可选能力。

退路：关闭观察器仍可完成主任务，回退固定配置主模型，关闭推断不影响用户明确纠正与删除。

Pi 更新、项目推进与离线学习独立演进

每一类能力先证明自己的边界和净收益。

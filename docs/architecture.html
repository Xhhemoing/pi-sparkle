Pi 提供模型与工具循环。Pi-sparkle 在它之上组织目标、权限、候选改动、验证和恢复，形成一个可直接工作、按需扩展的模块化单体。

按职责划边界，
让变化停在该停的地方。

界面变化不应牵动检查逻辑，Pi 升级不应散落整个项目，插件不应直接接管内部状态。层次的意义是限制影响范围。

为什么采用模块化单体？

先保持一个部署单元，减少跨进程、跨服务协调。只有真实独立消费者或交付需求出现，才考虑拆包；职责清晰先于目录数量。

协作可以双向，权限不能倒流。

检查结果与运行事件可以返回控制者，观察者也可提交建议；它们不能因此改写授权、认领任务或批准应用。

三个入口怎样接入，Pi 为什么有两个适配边界？

CLI 解析配置后调用已有 run / develop；Pi 扩展翻译宿主上下文并复用宿主模型与认证；嵌入应用未来通过窄 host 入口连接。目标入口还不是已发布的稳定公共 API，各入口也不因此自动拥有同等写入能力。

src/pi-adapter/ 是出站执行适配器，连接 core / ai；extensions/pi-sparkle/ 是入站宿主适配器，允许 coding-agent。standalone 自己管理运行，原生扩展使用宿主提供的能力。两条路径分别验收，不把安装了新 CLI 等同于内部内核已升级。

每个核心，拥有明确的决定权。

一个任务贯穿四类职责。输入和结果可以流动，但谁决定行动、谁管理写入、谁认可证据，需要始终明确。

任务与授权

掌握目标和行动决定权。

输入
用户目标、范围、已有授权、当前要求，以及队列、源码和未决效果等事实。
输出
下一步动作：继续、检查、范围内修复、暂停或准备关联任务；明确本次执行和验收所依据的要求。
谁决定
宿主任务控制者作出行动决定。用户显式要求可更新当前输入；观察者只提交发现，不产生授权。
如何协作
读取状态层，调用已有执行路径，并消费检查结果。项目模式由 controller 在锁内选择、认领；直接任务不强制进入队列。
为何独立
把“要做什么”与“怎样执行”分开，避免模型、插件或重试逻辑偷偷扩大任务范围。

已有：DevelopmentController、NativeWriteSession 与宿主入口。待整理：统一薄入口和任务输入投影，不新建第三份任务状态。

执行与资源

拥有运行生命周期与资源责任。

输入
控制者给出的动作、候选工作区、上下文、模型配置与适用资源约束。
输出
工具与运行事件、结果或失败、已知用量与未知部分，以及取消后是否真实结束的状态。
谁决定
执行层按已给定配置调度、重试和停止；不重新定义目标或验收。模型升级发生在规则允许的下一次 attempt。
如何协作
通过 Pi adapter 调用引擎与工具；使用工作区端口；将运行事实送入事件记录。取消后须确认进程与效果，再交还写入责任。
为何独立
Pi 接口、供应商故障和进程清理集中处理，避免各模块重复重试或把“已发取消”误认为“已停止”。

已有：run/coordinator、flowchart-run、pi-executor。待整理：两条路径共用必要生命周期端口；进程树可靠停止仍需真实验收，不增设调度器。

工作区与检查

把改动与被验证的对象对应起来。

输入
当前源码、任务范围、候选改动和宿主检查要求；按需接收上下文与诊断贡献。
输出
相关代码上下文、隔离候选、文件差异、诊断和与精确候选绑定的检查证据。
谁决定
宿主检查定义约束验收；诊断给建议，可信验证路径确认当前候选。模型自述、缓存或插件不能签发应用权限。
如何协作
为执行者提供读、搜、改、查；将实际检查结果返回控制者。源码或定义变化后重建候选或重新验证。
为何独立
分开生成与验证，让语言插件和检索策略可替换，同时保持已有严格 develop 的验收语义。

已有：context、worktree、independent-check、recipe-check。待完善：局部工具、上下文选择和稳定诊断贡献入口。

状态与恢复

保留事实来源，恢复前先对账。

输入
任务认领与状态变化、外部效果意图和收据、运行事件、候选与源版本。
输出
可重放的执行记录、当前权威事实、未决效果与可继续条件；项目进展只是这些事实的组合视图。
谁决定
各存储只权威地回答自己的问题；恢复逻辑据此核对，而不从一条 SUCCESS 或缺少日志推断全部完成。
如何协作
供 controller 认领、检查依赖与继续；供执行层记录事件和效果。迟到收据与用量保留，过期提案不能改写新任务。
为何独立
区分“任务说完成了”“外部操作是否发生”“源码是否集成”，避免崩溃后重复写入或错误解锁后继任务。

已有：WorkItemStore、ActionLedger、event-store / replay 与 Git。目标：清理依赖和恢复边界，不建第二套 ProjectState 真相。

实际源码映射与边界在 framework.md 持续维护。这里的四个职责是代码组织方向，不表示它们已被拆成四个包。

动作沿调用链推进，
证据回到各自的事实源。

以已有严格开发路径走完一次任务：控制者负责推进，执行者产生候选，检查路径核验当前改动。普通直接任务可省去队列编排，但不能把不明效果当成成功。

  1. 01 / 输入确定与认领
  2. 02 / 执行生成候选
  3. 03 / 证据核验改动
  4. 04 / 交付接受与集成
  5. 05 / 继续对账与恢复

控制者建立本次行动边界

宿主定义目标与检查要求。DevelopmentController.runNext() 检查依赖是否已进入当前源，并在锁内选择、认领任务。项目协调层只调用它，不能先做一次 claim 再把任务交给它。

控制流：入口 → controller → 既有执行路径。事实流：定义、状态与 claim 由 WorkItemStore 管理；当前源由 Git / 工作区核对。

执行层在候选工作区中运行

controller 进入 NativeWriteSession，先记录相关效果意图，再创建候选并调用已有 run / Pi executor。Pi 使用上下文和工具完成改动；运行层接收事件、失败与用量。范围内修复沿已有会话继续，避免每一步重建任务系统。

控制流：执行器 → Pi adapter / 工具 → 候选工作区。事实流：执行过程进入 run events；受管外部效果的意图与收据进入 ActionLedger。

检查验证的是当前候选

诊断帮助定位问题，宿主检查验证约定行为。检查通过后候选可进入 ready-for-review；它表示可审阅，尚不等于已接受或已集成。失败与证据返回同一控制者决定下一步。

控制流：候选 → 宿主检查 → controller。事实流：检查结果绑定精确候选与定义；候选变化使旧结果不再适用。

接受候选与应用到源码是两个动作

review 解释历史证据，accept 对当前候选重验并显式接受，应用仍是独立一步，按既有明确授权执行。无需重复索取已有授权，但不会因为模型说完成就跳过应用边界。

控制流：审阅 → 新鲜验收 → 单独应用。事实流：接受状态与实际源状态分别保存；后继任务必须核对前置结果已进入源码。

中断后先回答“发生了什么”

恢复读取任务状态、效果收据、运行记录与当前源码。缺失收据不证明外部写入没有发生；未知效果需对账后才能重放。基线改变则重新建立候选或验证，不能借旧通过记录继续应用。

控制流：恢复核对 → 允许继续 / 阻塞受影响动作。事实流：保留原始事实，重建进展视图；无关且已授权的本地工作可以继续。

四种事实，回答四个不同问题。

WorkItemStore任务与认领
项目工作项的定义、依赖、claim 与生命周期状态。它不能替代对当前源码是否集成的核验。
ActionLedger外部效果
受管动作的意图、结果、收据与未决状态。超时或断连后，用它核对效果，而非盲目重试。
run events执行历史
一项工作内部的运行、尝试与生命周期事件；checkpoint 和 inspect 由此形成投影。日志不授予验收或应用权限。
Git / 工作区代码事实
当前源、候选、差异与实际集成结果。“任务已接受”不能代替“源码已包含改动”。

粒度不同：一次 run 完成 ≠ 项目工作项已接受 ≠ 改动已进入源码。例如登录修复运行结束后，候选仍可能等待接受；接受后仍可能等待显式应用。ProjectSnapshot 是项目发现快照，整体进展由这些事实组合读取。

已有严格路径：上述 controller、候选、检查和显式应用机制已存在。仍需实施：统一轻任务入口与动态接续；本图不表示所有入口已经合并，也不关闭可靠停止等开放条件。

分清问答、行动、纠正与继续

“看看进度”读取状态；“把标题改一下”进入局部任务。

“能不能把背景换白”可能是行动请求，要结合上下文理解。纯解释不创建任务；纠正绑定被纠正的目标。优先复用当前对话模型的工具选择，日常每轮无需额外分类 agent 或规划会。

知道原命令名字不是使用前提。底层仍保留 CLI，供脚本、调试和高级操作使用。

把“这个”“刚才”“继续”绑定到真实工作

显式点名优先，其次使用仍有效的当前任务焦点。

从宿主记录取得项目、工作项、候选和消息引用；模型不凭空造 ID。已有充分授权持续有效。只有多个对象都合理、缺少关键事实或授权时才询问，不能把聊天中的推测当作确认。

检索资料和插件诊断只是证据；“继续”也不会自动授予发布、删除或跨项目权限。

自然语言落到有结构的操作请求

单任务走直接入口，项目推进走已有 controller 与队列。

宿主验证参数、范围、检查器与能力后调用函数。检查配置可继承项目默认值，用户无需输入命令路径或重复填写金额。已有的严格上限和检查条件继续生效。

用户原话不直接拼成 shell。自然语言表达应用意图，也仍需宿主绑定精确候选并签发能力；模型不能替自己签发授权。

把结果讲清楚，而不是展示一串参数

展示改了什么、检查怎样、哪里阻塞、下一步是什么。

默认交付简明结果，证据与细节可展开。运行结束、工作项接受、源码集成分别读取对应事实。失败、取消和未知效果必须如实保留，不能被对话摘要改写为成功。

一次已经完成的操作可以查询结果；对话重连或重复消息不应把它再执行一遍。

已有基础与待接线：原生扩展已有只读委派及受签发句柄约束的应用工具；实验性 startDevelopmentTask 已能执行直接开发任务。统一的自然语言路由、宿主自动装配与焦点管理是本次提出的接线方案，尚未实现。

哪些操作可直接做，哪些需要补充信息？

明确的状态查询、解释，以及已有授权内的可逆局部任务可以直接推进。多义指代、缺少可靠检查器或没有相关权限时，先说明缺口；只询问真正影响结果的内容。关键区别是目标、证据和授权是否充分，不是任务文字多长。

当前直接入口仍要求宿主提供 executor 与验证命令，不能把“实验性函数存在”说成“对话端到端已经接好”。完整方案见 对话入口与长期任务衔接。

第二天，你说

继续这个项目。

摘要负责定位，底层事实决定下一步

读取：目标 / 决策 / 阻塞复核：任务 / 收据 / 源码

按需装入当前要求、项目摘要、任务状态和相关证据。旧摘要与新源码冲突时更新摘要；多个项目都合理时才问一次对象选择。即使换一个聊天，也能通过持久化记录恢复项目。

小任务什么时候升级为项目工作项？

出现跨天跟踪、依赖、交接或用户明确要求纳入计划时再升级。引用现有 run 与候选，补齐工作项定义和必要检查，不从头重做，也不把历史执行结果自动标成已验收。

项目里的一次解释或普通询问仍可只是对话。任务大小决定编排需求；真实影响决定检查强度。

聊天很长时，如何避免遗忘、串任务和成本膨胀？

每轮优先选择当前要求与授权、项目目标、当前任务和相关证据。其余历史按需检索。摘要保留来源、有效范围、未决问题和纠正关系，不把所有聊天反复塞进模型。

任务完成状态仍只读自既有事实源；项目 A 的临时偏好不进入项目 B。切换焦点只改变对话关注点，不转移写入权或验收权。先用现有文档与事件检索，按真实需要再增加记忆与后台能力。

模型路由如何控制成本？

先尊重用户指定并筛选工具、上下文、供应商等能力，再在已测可用配置中选择合适成本档。先区分环境、工具、provider 与功能失败，只有功能不足或高不确定性才考虑升级模型。没有校准数据时使用配置主模型。

费用包括失败、取消、重试和辅助分析；未知部分不记为零。当前 CostGate 是回合后的观测停机，严格调用前预留与跨层结算仍需实现和验证。

怎样防止框架过饱和？

默认一个执行者，未触发插件不执行入口，研究和晋升模块离开默认运行路径，每类状态只有一个权威。观察额外模型调用、启动依赖、首次有效编辑时间、返工和费用覆盖率。没有净收益证据的新能力不进入默认路径。

跟进 Pi，以兼容行为作为入口。

产品不永久绑定一个内核版本。每项运行仍记录自己的精确组合，保持恢复和问题复现的依据。

候选发现离开任务关键路径

先用已安装、已合格的组合接任务。

管理命令或后台检查发现候选。选择自动稳定通道后，兼容更新可按该策略采用，无需每个小版本再次确认；离线与精确版本模式保留。

验证行为，不只检查方法名称

独立安装、独立进程，检查事件、工具、取消与停止时序。

例如停止钩子即使只是改名，调用时间变化也可能让费用更新晚于下一次请求。资格测试必须覆盖“观察本轮用量后，在下一次 provider 调用前停止”。

破坏性变更需要更新适配器，完成后仍走同一认证流程。任何未来版本零适配不在承诺内。

一个新运行绑定一组已验证组合

候选合格后发布资格记录，再更新采用指针。

新 root run 选择 runtime generation，子任务和重试继承。首期优先一个 root run 一个受管进程，不先建设常驻多版本池。

内嵌执行器与宿主 Pi 扩展是两个兼容边界。宿主本体更新需要新进程，扩展 reload 不能证明已加载内核完成更新。

在途任务继续原组合，恢复也有原绑定

候选失败保留已知可用版本，已有外部效果不盲目重放。

运行引用和恢复需要共同阻止旧组合被过早回收。共享状态格式迁移先保留副本并确保旧写者停止，回退代码不等于自动兼容新数据。

身份遵循 ADR-008：不透明版本化标识与必要的精确字节比较，不新增第一方加密哈希或防篡改保证。

当前明确要求优先，任务结束不自动改写永久偏好。

能查看、能纠正，也能删除

偏好记录为什么生效、用于哪里、何时过期。

跨项目不混用约定，弱推断不能覆盖显式表达。删除使派生缓存失效，并阻止旧来源把同一事实重新记回来。没有相关证据时使用默认，不编造用户画像。

偏好影响表达和协作方式，不产生部署、花费或写入授权，也不允许隐藏真实失败。

推断策略走受控学习闭环

记录事实，分清原因，离线比较，再有限试用。

代码错误、provider 故障、需求变化和表达不合适分开归因。正确性与实际验收是门槛，再比较返工、费用、延迟及用户纠正。满意度只是一项反馈。

第一阶段沿用现有批准与回滚流程。之后可在一次性启用的有限范围自动试用低风险策略，前提是监测、停止和回滚真正可用。

长期自优化能不能修改框架自身？

可以把改进建议转成普通开发任务，产生可检查候选，并复用已有授权、检查与应用流程。低风险策略自动试用不包括偷偷替换运行中的内核、改动权限或检查器。模型推断的策略和用户明确设置是不同路径。

能力激活时发生什么？

先读取声明并匹配需要，首次请求时再加载。并发激活共享一次加载，验证后一次发布，失败不留下半注册状态。

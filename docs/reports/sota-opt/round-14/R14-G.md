### §3.1 规模退化标定（N 阶梯 / E 阶梯 + I/O 共增 + 越线点）

方法：对切片三个规模敏感热函数做 4×/16× 阶梯，检验每单位成本是否随
规模退化（1.0 = 完全线性）；同时在**同一 N 阶梯**上测 checkpoint 持久
写 I/O，检验支配关系是否随规模反转。脚本 `tmp-r14g-scale.ts`
（sha256 `8ab52348…`，附录 B）。

```text
validateFlowchart N=16/64/256/1024: 8.586 / 31.072 / 126.150 / 557.852 µs
  每节点 537 / 485 / 493 / 545 ns -> 64× 规模比 1.02（线性；Kahn shift 不显形）
replayRun E=300/1200/4800: 0.707 / 2.556 / 9.711 µs
  每事件 2.4 / 2.1 / 2.0 ns -> 16× 规模比 0.86（亚线性）
validateCheckpoint N=48/192/768（含 JSON restore）: 246.6 / 978.2 / 4286.7 µs
  每节点 5137 / 5095 / 5582 ns -> 16× 规模比 1.09（线性）
CheckpointStore.write 持久 N=48/192/768（30/116/462 KiB）: 596.6 / 1149.8 / 3443.8 µs
越线点（落地线取 10 ms/run）：
  N*（规范 run 计算面 32× validateFlowchart）≈ 574 节点/流程图 = 生产 16 的 ~36×
  validate-on-read 每交互命令（矩阵 cp.read=1）：N=48/192/768 时 0.25 / 0.98 / 4.29 ms
  E*（单次 replayRun 越 10 ms）≈ 4.9×10⁶ 事件（生产 ~300）
I/O 共增：N=48/192/768 时规范计算 0.84 / 3.35 / 13.39 ms/run vs
```

### §3.3 GC/分配预算审计

方法：`--expose-gc` 下 gc 围栏测每次热路径调用的堆分配量；再以
PerformanceObserver 观测一个模拟 run 计算面（32 轮 × {1 vf、2 次
checkpoint materialize+stringify、3 次 readAll 校验份额、1 次
checkpoint validate}）的全部 GC 事件。脚本 `tmp-r14g-alloc.ts`
（sha256 `a9fe30a1…`，附录 B）。

```text
每调用分配（N=48 checkpoint 美化 JSON = 29.8 KiB）：
  supervisor.snapshot()（structuredClone） 17.2 KiB
  materializeCheckpoint                    18.7 KiB
  JSON.stringify(checkpoint, null, 2)      35.9 KiB
  validateCheckpoint(JSON.parse(json))     44.6 KiB
  replayRun 300 events                     11.0 KiB
  validateFlowchart 16n join4               5.4 KiB
  validateEvent AGENT_EVENT                 0.3 KiB
每 run 计算面分配预算 ≈ 10.7 MiB/run（66× 快照+物化+字符串化、96×
  readAll 校验份额、32× validateFlowchart）
一个模拟 run 计算面：wall 32.4 ms、GC 事件 2 次、GC 合计 1.91 ms
```

**裁决**：无分配风暴——整个计算面的 GC 代价 **~1.9 ms/run**，不及
I/O 地板（93.6–101.4 ms）的 2%，且为 scavenge 亚 ms 切片、无长暂停。
这给「分配向」候选族一个**整体上界**：structuredClone→浅拷贝
（S3-G-1，其 2.8–8.6 ms 全 run 上界本就含隔离性降级否决，本轴给出更紧

削减（S4-G-6 磁盘字节发散封死）等全部候选即使**全额清零**也 < 2 ms，
低于落地线一个数量级。GC 旗标调优（semi-space 等）属 bin/运行时旗标
面，出切片且同受此上界压制。**该轴不产生任何候选。**

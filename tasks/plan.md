### Confirmed acceptance details (2026-10-25)

**TS:** Missing `typescript` or `tsconfig` is infrastructure failure with preparation guidance; a compiler that runs and finds a type error in a declared passing baseline is an unexpected/undeclared RED with code-fix guidance. Neither is accepted as a named business RED. Keep distinct machine-readable reasons and messages; the existing failure exit code is `1`, so distinct numeric codes are not required. Any public JSON/CLI change needs compatible pinning tests and review. Actual REDs: type-invalid source still passes `node --test` but preflight refuses with zero model calls; a worker-introduced type error fails final acceptance with source unchanged; missing compiler and config refuse separately. Explicitly supply dependencies, never auto-install. Charge real compiler startup and every check to the cumulative check allowance; measure instead of assuming a fixed cold-start duration.

**Rust:** Real missing-toolchain and uncached-dependency cases must refuse with zero model calls, unchanged source and observed settlement. Match nonzero exit plus known stable diagnostic features; unknown failures keep generic refusal and private evidence, never guess. Guidance may describe selecting an already installed Rust environment before init, or owner-run `cargo fetch`/`cargo vendor` preparation outside the product's offline run; no automatic download, toolchain install or network. Test public hints exclude local private paths, secrets and raw stderr. Preserve `RUSTUP_AUTO_INSTALL=0`, offline/locked checks and the environment allowlist. Node/cargo executables, explicit Rust homes/toolchain and output locations already bind the draft to its init host; docs/init must say to regenerate and review on another host, and avoid committing/sharing an unreviewed machine-bound draft. Do not re-resolve only preflight or read a fresh environment for each check. The proposed cwd fix is withdrawn: the existing test entrypoint already sets `cwd: REPO`.

**B1 trust and limits:** Authority comes from the owner's new request with TaskSpec and explicit source/candidate selection; freshly executed fixed checks provide current acceptance evidence. Artifact, Ledger and Git metadata can all be edited by the same user: record consistency and hashes do not authenticate history or recreate an old live capability. Reuse existing Git identities, exact byte/index checks and Ledger mechanisms where applicable; do not add five new hashes by default. B1 proves the current candidate satisfies the newly authorized checks, not independently that it is the previously accepted candidate. Missing/unsupported binding data or inability to establish the required association must refuse; do not silently upgrade old artifacts. Do not promise resistance to a same-user adversary controlling host code, owner input and all records. Tampered records must not skip fresh verification or direct an unauthorized action.

B1 is **zero-model, source-unchanged finite verification**, not pure read-only execution: checks and evidence can create effects. Define a separate finite deadline/check/output allowance with cancellation and actual settlement; do not rerun prepare/install or reset, restore or rewrite original worker/USD/budget history. Include B2's mandatory rechecks in an explicit bounded allowance; repeated resume must not silently renew old authority. Unknown historical effects remain unknown even after successful fresh checks; an untrusted `settled=true` cannot clear reconciliation.
